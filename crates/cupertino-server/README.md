# cupertino-server

The Smithay 0.7 Wayland compositor of Cupertino, as a library (`cupertino_server`) and a binary (`cupertino-server`). This is its design, for people changing the compositor or the shell processes that talk to it: command line, architecture, configuration files, protocols, tests and open issues.

Window policy comes from `cupertino-wm`. Server-side decorations, window effects and input handling come from `cupertino-decorations`, `cupertino-effects`, `cupertino-input` and `cupertino-keyboard`. Shadows, rounded corners and material passes run as GLES shaders. The overview is driven by `cupertino-overview`. The notifications, menu bar, launcher and dock run as separate Wayland clients that the server starts and restarts (*Shell processes*).

Contents: [Run it](#run-it), [Run on hardware](#run-on-hardware), [Command line](#command-line), [Architecture](#architecture) (window policy, rendering, material pass, protocols, clipboard, displays, session bus, shell processes, accessibility, keybindings and configuration files, keyboard, launcher, overlays, screenshots, notifications, idle, log out), [Integration points](#integration-points), [Tests](#tests), [Open issues and approximations](#open-issues-and-approximations).

## Run it

Headless `scripts/capture.sh` and `scripts/session.sh` search your user pack (when there is one), then the
original checkout icon pack. An explicit `CUPERTINO_ASSET_DIR` replaces both; an empty value selects the built-in fallback.
For nested development runs, set `CUPERTINO_ASSET_DIR="$PWD/data/assets/cupertino"`.

```bash
cargo run -p cupertino-server -- --winit                       # nested window (development)
cargo run -p cupertino-server -- --udev                        # TTY: logind + DRM/KMS + evdev
cargo run -p cupertino-server -- --headless --screenshot out.png --exit-after-screenshot
```

The server and every process that draws text or icons read the asset packs of `cupertino-assets`: `CUPERTINO_ASSET_DIR` first, then the user and system packs, then the built-in fallback; a missing pack or file never stops a start. The server's text (title bars, HUD, accent popup) and cursors come from them, and the processes it starts inherit the variable.

The server's text (title bars through `Decorations`, the input-source HUD and the accent popup through `OverlayText`) is drawn with the optical size of the output's scale: both set it from the scale they draw at.

The compositor prints `WAYLAND_DISPLAY=<socket>` once it listens. The socket is the first free `wayland-N` of `XDG_RUNTIME_DIR`; when all 32 are taken (other sessions, or other servers started by tests running at the same time) it is `wayland-cupertino-<pid>-<n>`, so a server always finds one. `tests/socket_names.rs` starts 40 at once. Start clients with that variable. `Super+Return` starts a terminal (`xdg-terminal-exec` for the user's default terminal, `$TERMINAL`, then `foot`, `alacritty`, `kitty`, `wezterm` or `xterm`, whichever exists first; configurable with `terminals`, where `$NAME` stands for the program an environment variable names).

## Run on hardware

The TTY backend needs a seat of its own: logind refuses control of a session that has a controller, so it cannot start inside a running desktop. Start it from a free text console, or from a display manager's session entry (`cupertino.desktop`), and leave the desktop on its console.

Before the first run, in case the server hangs instead of stopping (an EGL or GBM start-up that never returns, a page flip that never completes): logind takes the keyboard from the kernel, so the console switch keys and `Ctrl+Alt+Backspace` need a live compositor.
- `sudo sysctl kernel.sysrq=1` for this boot (it is 16 by default, which allows `sync` only). The last resort is then `Alt+SysRq+R`, `E`, `I` (keyboard back to the kernel, terminate all, kill all) and `Alt+SysRq+S`, `U`, `B` (sync, remount read-only, reboot).
- Optional: `sudo systemctl start sshd` and a second device on the network, to kill the server from outside (`pkill cupertino-server`).
- Save your work in the other session.

1. Log in on a free console (`Ctrl+Alt+F3`), then `./run-cupertino.sh` from the checkout. It builds, runs `cupertino-server --check-hardware` and stops with the reason when the machine is not ready, and starts the server with `--run-for 900` unless you give `--run-for` yourself (`CUPERTINO_RUN_FOR` changes the default, a whole number of seconds). The server runs under `timeout -k 10 <limit + 30>` inside the session bus: a server that hangs past its limit gets SIGTERM and, ten seconds later, SIGKILL for whatever is left of its process group, and the kernel and logind give the console back. A run without a limit is refused unless `CUPERTINO_ALLOW_NO_TIMEOUT=1`. The script runs the binaries it just built, from `CARGO_TARGET_DIR` or the checkout's own target directory, and prints which one.
2. **Leave.** `Ctrl+Alt+Backspace` (`quit-compositor`) quits the server, and `Ctrl+Alt+F1`..`F12` switch console. Both are reserved actions: no application's shortcut inhibitor takes them. From another console or over ssh, `pkill cupertino-server` ends it too.
3. **Logs.** `~/.local/state/cupertino/server.log` (`$XDG_STATE_HOME`, or `CUPERTINO_LOG_FILE`; mode 0600) holds everything the server logs, including the GPU, driver and kernel it found and any panic or fatal signal with its backtrace; the previous run's log is `server.log.1`. `CUPERTINO_LOG_FILE` is written in every mode (offscreen crash tests use it), and the server removes it and `CUPERTINO_SESSION_END` from its environment, so a server started from its clients writes neither. Warnings and errors also reach standard error, and an error that stops the start (the checks below, logind, GBM, EGL) is written to the file as its last line, `the server stopped: ...`. What the processes print, including a start that fails before the log is opened, is in `~/cupertino-tty.log`. `RUST_LOG` changes the filter.

**NVIDIA.** `--check-hardware` reports the driver, and with the `nvidia` driver it requires `nvidia-drm.modeset=1` (kernel command line, or `options nvidia_drm modeset=1` in `/etc/modprobe.d`; `cat /sys/module/nvidia_drm/parameters/modeset` must print `Y`), and warns when `/usr/lib/gbm/nvidia-drm_gbm.so` (package `nvidia-utils`) is missing. The same check runs at the start of `--udev` and refuses to start with the fix. Explicit sync (`linux-drm-syncobj-v1`, used by Chrome and Electron on NVIDIA) is offered when the kernel supports it; it has not been run against the NVIDIA driver yet, so the first thing to check on the hardware is the log line `explicit sync (linux-drm-syncobj-v1) is offered` and that Chrome starts and draws.

### From the display manager

The package installs the session entry `cupertino.desktop` (it runs `/usr/bin/cupertino-session`) next to the other Wayland sessions, so GDM lists **Cupertino** in its session chooser. The packaged session is the same server as above; the script around it makes a bad first login recoverable:
- When the compositor ends, for any reason, the script ends with the compositor's status and the display manager shows its login screen again; do not enable automatic login for this session while it is new, or a crash would log in again at once.
- `~/.local/state/cupertino/session.log` gets one line per start and end (normal end, exit status, the signal that ended the compositor, or ended by the watchdog); `server.log` there has the compositor's own log. When the compositor ends with an error, a panic on its main thread or a lost rendering context, the end line also has the reason: `cupertino-session` names a file in `CUPERTINO_SESSION_END` (`session-end` in that directory, removed before the start and after the end), and the server writes one line there (control characters as spaces, at most 400 bytes). After a panic or a lost context the teardown may take 2 s; then the server exits at once (`_exit`, no exit handlers), so a driver call that hangs does not keep the display manager's login screen away. SIGABRT (an abort in a library, a panic while panicking) and SIGSEGV (a fault, a stack overflow) are caught: the handler writes `the server was ended by SIGABRT` (or `SIGSEGV`) to that file with no allocation, then `fatal signal SIGABRT; backtrace:` and the backtrace to the log, then ends the process with the signal's previous action, so the status is still 128 plus the signal. The backtrace allocates and takes locks, which a crash inside the allocator may hold; an alarm of 2 s ends the process if it hangs (status 142). A fault in the handler ends the process at once (both signals are blocked while it runs). SIGSEGV runs on an alternate stack of 1 MiB on the event loop's thread. `--crash SECONDS:panic|abort|overflow` crashes the server on purpose for the tests (`tests/session-end.rs` runs it offscreen through `cupertino-session`: the session ends within 5 s of the crash, with the reason in `session.log` and the backtrace in `server.log`). Other signals (SIGBUS, SIGILL, SIGKILL) leave no reason; the line names the signal.
- A first login can be bounded the way `run-cupertino.sh` bounds a run: write a whole number of seconds into `~/.config/cupertino/session-limit` (or set `CUPERTINO_SESSION_LIMIT`), for example `echo 600 > ~/.config/cupertino/session-limit`. The compositor stops after that long, and an outside `timeout -k 10` ends it 30 s later if it hangs. Remove the file for a normal session. A value that is not a whole number is ignored and logged.
- The same pre-flight list as above applies (`kernel.sysrq=1`, save work first), and the machine checks of `--check-hardware`.
- **Shared user bus.** Under GDM the session runs on the user's systemd bus, and the user manager and D-Bus activation start portals and services with the environment they already hold (another desktop's `WAYLAND_DISPLAY` and `XDG_CURRENT_DESKTOP`: wrong portal backend, file choosers and screen sharing that do not work, long stalls in GTK programs). Once the compositor listens, `activation_env.rs` puts `WAYLAND_DISPLAY`, `XDG_CURRENT_DESKTOP=Cupertino` and `XDG_SESSION_TYPE=wayland` in the manager (`SetEnvironment`) and the bus's activation environment (`UpdateActivationEnvironment`) and starts `cupertino-session.target` (installed in `/usr/lib/systemd/user`, bound to `graphical-session.target`, as the sway and niri sessions do). `cupertino-session` stops the target and removes the three variables when the compositor ends, a crash too. A user has one systemd manager for all sessions, so when `graphical-session.target` is already active (a GNOME session of the same user is still running) nothing is changed and the log says so; log that session out first, or the portals and services on the bus keep serving it. The session's own X display (*X11 applications*) is published as `DISPLAY` and `XAUTHORITY` as well. Without one (`xwayland-satellite` not installed), a `DISPLAY` and `XAUTHORITY` that an earlier desktop left are removed from the manager and emptied in the activation environment, since a program that finds `DISPLAY` set prefers it to Wayland; `cupertino-session` removes all five variables when the compositor ends. If the session command was killed before it could stop the target, the next session finds `cupertino-session.target` still active, stops it and goes on. The target counts as a leftover only when nothing listens on the `WAYLAND_DISPLAY` the manager holds, or when that is this session's own display name (a compositor that took over the socket name of the session that was killed); a second Cupertino session of the same user whose compositor still answers is treated like any other active session and left alone. On a private bus (`dbus-run-session`, `run-cupertino.sh`) there is no systemd user manager and nothing is done. With `dbus-daemon` (not `dbus-broker`) the activation environment cannot be unset, so the display of an ended session stays in it until the next session overwrites it.
- **Notifications.** `cupertino-notifications` asks for `org.freedesktop.Notifications` without taking it over. On a shared bus where another daemon owns the name (GNOME's, while its session runs), it says so and ends normally (status 0), so the supervisor leaves it stopped; the notifications of this session then go to the other daemon. With one graphical session per user the name is free. The process is not started again in that session, even if the other daemon goes away; the log line `another notification daemon owns org.freedesktop.Notifications` in the shell process's output says why there are no notifications.
- Not verified: how GDM treats the session on a real machine (VT, restart after a crash); the first login is the test, and `Ctrl+Alt+Backspace` ends the session as on a console.

## Command line

Without a backend flag the server runs nested when `WAYLAND_DISPLAY` or `DISPLAY` is set, else on the TTY. Giving more than one of `--winit`, `--udev` and `--headless` is an error.

| flag | default | effect |
|---|---|---|
| `--winit` / `--udev` / `--headless` | nested if a session display exists, else TTY | backend |
| `--size WxH` | `1280x800` | nested window or headless output size |
| `--scale F` | host scale (nested), 1 otherwise; with `--physical-size`, the headless output's default size | output scale |
| `--physical-size WxH` | unknown | the headless output's physical size in millimetres, so it has a density, "looks like" choices and a default size of its own |
| `--connector NAME` | `headless-1` | the headless output's connector name; `eDP-1` makes it a built-in panel |
| `--extra-output NAME:WxH[@SCALE]` | none | headless: one more offscreen display right of the others (repeatable); with more than one display every screenshot is written per display, the first one's at the path given and every other one's beside it with its name added (`shot-headless-2.png`) |
| `--unplug SECONDS:NAME` | none | headless: unplug the display with that connector name at that time (repeatable) |
| `--appearance light\|dark` | from the configuration | material and shadow appearance |
| `--check-hardware` | | print what the TTY backend needs from this machine (primary GPU driver, the NVIDIA settings below) and exit with status 1 when something blocks it; opens no device, so it also runs inside a desktop session |
| `--dev-shell` | off | let any configuration file name the shell processes and the screenshot process, from any path (development and nested runs; see *Shell roles*) |
| `--spawn "cmd args" (repeat) | | start a client after startup on the compositor's socket |
| `--spawn-delay S` | `0.5` | seconds before the first `--spawn` command |
| `--pointer S:X,Y`, `--click S:X,Y`, `--right-click S:X,Y` (repeat) | | scripted pointer motion, left click or right click at time S (logical coordinates) |
| `--press S:X,Y`, `--release S:X,Y` (repeat) | | scripted left press and release at time S, to script a drag with `--pointer` |
| `--modifier-down S:MOD`, `--modifier-up S:MOD` (repeat) | | hold or let go of `shift`, `ctrl`, `alt` or `super` as a device would: through the key filters and the shortcuts, so a held Super opens no launcher but a Super pressed and let go alone does, and the focused client gets a real key event (menus that show alternates while a modifier is held) |
| `--time-scale F` | 1 | run model time (animations) at F times the wall clock, for example `0.2` to catch mid-animation frames |
| `--dbus` | off | start the session bus worker also on the headless backend (it always starts on the nested and TTY backends) |
| `--action S:NAME` (repeat) | | run a named action at time S (`overview`, `minimize`, `workspace-right`, `launcher`, `input-source-next`, `notification-center`, ...) |
| `--key S:CHORD` (repeat) | | press and release a chord at time S (`1:Super+space`, `2:Return`). It goes through the HUD / accent / key router, so a scripted power key is a tap, which the login process ignores. A key none of them takes reaches the focused client as real key events. |
| `--type S:TEXT` (repeat) | | type text at time S into the focused client, for example the launcher panel when it is open |
| `--accent S:CHAR` (repeat) | | open the accent picker for a character at time S, as a held key would after its repeat delay |
| `--hold-modifiers` | off | scripted shortcuts behave as if their modifiers stayed held (the input-source HUD stays open) |
| `--screenshot PATH` | | write the rendered output as PNG |
| `--screenshot-after S` | `3.0` | seconds after start at which `--screenshot` is taken |
| `--exit-after-screenshot` | off | exit once the screenshot was written |
| `--shot S:PATH` (repeat) | | several screenshots on a timeline |
| `--run-for S` | | exit after S seconds |
| `--no-menu-bar` | off | hide the menu bar (no menu bar reservation) |

`--screenshot` renders the output offscreen through the normal element tree (cursor included), so it works on every backend. Results of the last run are in `output/` (1280x800 unless noted):

## Architecture

```
backend (winit | udev | headless)  ──input──▶  events.rs ─▶ input.rs (KeyRouter, Action, ActionPlan)
        │                                          │                         │
        │ frame                                    ▼                         ▼
        ▼                                     state.rs  ◀── Command/Effect ── cupertino-wm (Wm::handle / tick)
   frame.rs ── build_output_elements ──▶ render/scene.rs ── LayerStack ──▶ [CupertinoElement] ─▶ OutputDamageTracker
                                                 ▲   ▲
                                      shell.rs ──┘   └── render/{shader_rect, clip, material, ui, programs}.rs
```

| module | role |
|---|---|
| `state.rs` | `Cupertino`: Smithay states, `Wm`, outputs, windows, shell; effect application, spawn, hit testing |
| `handlers.rs` | protocol handlers (an activation token presented for a surface that is not mapped yet is kept until its window maps): compositor, xdg-shell, decoration, dialog, layer-shell, seat, selections, dmabuf, activation, foreign toplevel list, fractional scale |
| `hung.rs` | hung applications: `Liveness` (the ping timing, pure) and `Pings` (one per client that owns a mapped toplevel): `xdg_wm_base.ping` every second, unresponsive after two seconds without a pong, responsive again at the next pong; `Cupertino::tick_hung`, `window_is_unresponsive`, `pointer_over_unresponsive`, `unresponsive_apps` |
| `force_quit.rs` | Force Quit: `Cupertino::force_quit_app` (an application that does not answer is sent SIGKILL at once; any other gets `xdg_toplevel.close` on each window and SIGTERM, and `tick_force_quit` sends SIGKILL `KILL_GRACE` = 3 s later to what is still connected), `kill_process` |
| `clipboard.rs` | the kept clipboard (copy of a client's clipboard, taken over when it exits), `Snapshot`, the data-control globals |

### Window policy

All policy is delegated to `cupertino-wm`; the compositor only translates.

**New-window placement** (`policy::Cascade`, the visible frame V is the usable area, or the stage frame while a window of the output is in the strip or hidden):
* The first window of an application is centred: `x = V.x + ⌊(V.w − w)/2⌋, a quarter of the vertical slack above it, its top on V's top when it is taller. On a 1920 × 1080 output under a 24 pt menu bar an 800 × 600 window opens at (560, 138).
* Each later window of the application cascades 29 pt right and down from the point its newest window on the same output left (so (589, 167), then (618, 196)). A start that leaves V wraps: a new column at `V.x + 14.5 k`, a new row at `V.y + 14 k`, both back to V's edge once the shifted start no longer fits or (rows) starts within 4 × 29 = 116 pt of the output bottom. The two offsets are kept per application, as the design keeps them per application process.
* Child windows are centred and then placed by the model (sheets, dialogs). The server restores no saved frames.
* the application identity standing for the design's window-controller class, the active output's bottom standing for the main screen's in the 116 pt bound. A stage holding only its centre group is not seen (the protocol carries no stage state), so its new windows are placed in the usable area.

* **Protocol to `Command`**: first buffer commit → `Map` (identity from `app_id`; without one, from the client: the application of its other mapped window, else the application its launch token named, else the desktop entry whose `Exec` program or `StartupWMClass` is the file name of the program it runs, only when root owns that file and every folder above it and nobody else may write to them (`process.rs trusted_executable`, `DesktopIndex::for_program`; several entries for one program name none), else the title; title, size hints, parent, modal flag from xdg-dialog, placement below). Title / hints / modal / parent updates → `SetTitle` / `SetSizeHints` / `SetModal` / `SetParent`. xdg move / resize requests → `BeginMove` / `BeginResize`, and the pointer is routed to `PointerMotion` / `PointerRelease` (`PointerMode::Model`). Maximize → `ToggleZoom`, fullscreen → `Fullscreen`, minimize → `Minimize` with the dock's minimize target. Activation → `FocusWindow` when the token rule allows it, else `DemandAttention`. Destroy / unmap → `Destroy`. Primary-modifier drags: left = move, right = resize (nearest corner).
* **Window kinds**: the kind (open / close transform, `cupertino-wm::kind`) comes from the protocol facts at map time, in the design's precedence (`window_kind`): modality (xdg-dialog-v1 `set_modal`); Wayland has no utility-window signal. The parent is `xdg_toplevel.set_parent`. The model maps a modal child as a **sheet** (hangs centred from the parent's title bar, slides down 32 pt while fading in over 0.26 s and back up on close), centres a parentless modal panel high on the usable area (cascading by 66 pt from the application's open panel), centres other children on their parent (approximate) and keeps plain windows unanimated. A modal child keeps the focus off its parent (`Wm::blocking_modal`); pointer events still reach the parent's surface.
* **`Effect` to protocol**: `Configure` → xdg configure (size minus insets, model states, activated flag). `RequestClose` → `xdg_toplevel.close`. `Focus` → keyboard focus and activated states. `SwitcherChanged/Closed` → the docks' switcher events. Window state changes → the dock's window feed. Everything else requests a redraw. Stacking, visibility, snap previews and workspace slides are read from the model at render time (`stacking_order`, `presentation`, `workspace_position`, `snap_preview`).
* **Title bar style**: `cupertino_app_effects_v1.set_titlebar_style` lets a client choose `WindowEntry::titlebar` before its window maps. `Unified`, `UnifiedCompact` and `Sidebar` (the last two from version 6) give the window no insets (its surface is the whole frame); the server draws only the window control buttons (a transparent strip of the style's row, 52 pt, 40 pt, or the 52 pt top of a full-height sidebar, `decor.rs`, with one cached `Decorations` per style) and the rim, the buttons take the pointer before the surface, and the rest of the strip belongs to the client, which moves the window with `xdg_toplevel.move`. Resize zones and the shadow are the server's. Tested in `tests/unified_titlebar.rs`.
* **Window buttons**: close, minimize and zoom follow the decorations' capability table (`decor::button_enabled`; a full-screen window does not minimize, so the title bar revealed over it has minimize disabled and a press there does nothing, as on the rest of that bar): a window can always be closed, so its group is always there, and a button the window cannot use (minimize disabled by its application, zoom disabled or a fixed size) stays in place, dimmed, and is no control: a press on it is the title bar's (no pressed look, nothing fires; past the drag threshold it moves the window, and a second press within the double-click time does the title bar's double-click action). The title bar is drawn again when any of the three changes. Tested in `tests/headless.rs` (`a_press_on_a_disabled_window_button_drags_the_title_bar_and_fires_nothing`).
* **Window buttons for assistive technology** (`decor_access.rs`): in a person's session on the hardware (not at the login screen, nor in nested and offscreen runs) the server publishes the buttons it draws on the accessibility bus with AccessKit's Unix adapter (`accesskit_unix`, as the toolkit's applications do): each window with server-side buttons that is mapped, neither minimized nor full screen, is a top-level object of the server's, a window named for its controls ("Notes window controls", `controls_name`, so it is not taken for the client's own window of the same title), with three push buttons in reading order, Close, Minimize and Zoom, their bounds in the frame and the window's place on the screen. A full-screen window's buttons are published while its title bar shows, revealed with the menu bar over it (minimize disabled, as drawn, and bounds in that bar), and withdrawn when it hides. An enabled button offers the press action; a disabled one is reported disabled and offers none. The zoom button has no long press nor menu for the pointer, so the press is its only action here too. A press asked by an assistive technology reaches the loop through a channel and does what a click does (`Cupertino::press_published_button`): only on a button published enabled, of a window published now, while the session is unlocked, and `press_window_button` checks the button again. The buttons are computed again only when something may have changed them: a model command, a redraw request or a commit (`ButtonAccessibility::invalidate`), the lock changing, or an animation running (and the pass after it ends); idle passes of the loop compute nothing, and only windows that changed are sent; nothing is computed without a sink. While the session is locked every window's object is withdrawn, as are those of windows that close, minimize or go full screen. Nothing is exported until an assistive technology turns accessibility on. The window's client publishes its own content as a separate object. Tested in `decor_access.rs` and `tests/headless.rs` (`the_window_buttons_reach_assistive_technology_with_their_names_and_states`), with a sink that records the trees in place of the bus.
* **The menu bar's menu keeps its window active**: when the keyboard moves onto the menu bar (one of its menus, or the bar in its keyboard mode), the key window stays activated and, after the keyboard leave its client heard, gets a configure that says so again (`Cupertino::keep_activated_under_menu_bar`), so the application whose menu is open keeps drawing as the window in use. Moving between the bar and its menus sends nothing more; the keyboard coming back sends nothing; another window becoming the key window deactivates it as usual. Tested in `tests/menu_bar_v1.rs`.
* **Decoration negotiation**: a toplevel that binds xdg-decoration and does not ask for client-side decorations is decorated by the compositor (`WindowEntry::server_side`). Its insets (title bar height from the decoration metrics) are added to the model frame, configures carry the surface size, and content sits below the title bar. A client that requests client-side decorations, or never binds the protocol, keeps its own and gets no insets. With `decorations = false` in the configuration every window gets `ssd_insets` and no decorations. A window configured full screen has no insets, no title bar and no decoration hit zones (`WindowEntry::insets`): its client gets the whole output, and the decorations come back with the next configure that is not full screen. The green button of a full-screen window leaves full screen (`cupertino-wm` `toggle_zoom`).
* **Output changes**: a resized output (nested window, hot-plug mode change) sends `Command::SetOutputRect`, and the model refits full-screen, zoomed, tiled and normal windows of that output.
* **Time**: `Cupertino::now` is the monotonic presentation clock in seconds (`fixed_time` overrides it for tests, `--time-scale` scales it). `tick runs every loop iteration before rendering.
* **Animated frames** are drawn by `plan_window`. At rest the committed surface size wins (no stretch). While the model animates only a window's frame (zoom, tile, full screen, a drag out of a tile) the content is never scaled: it is drawn at the size the client committed from the frame's top-left corner and cropped to the frame with the decorations and the window's backdrops; until the client draws a larger size the window keeps its own. A configure that shrinks a window during such an animation asks the client for a size that covers every animated frame (the larger of its size and the model's on each axis); the model's size is sent when the animation ends (`Shrink` in `WindowEntry`), and until a commit acks that configure the window stays cropped to its frame (whatever size the client then draws: the size is a hint to a floating toplevel). While a window minimizes or takes a presentation scale, the content is scaled to the animated rectangle (minimize collapse towards the target, then presentation scale about the centre) with `RescaleRenderElement` and a mask in final coordinates.

### Rendering and element order

Bottom to top (`SceneLayer`): wallpaper, layer-shell background, layer-shell bottom, overview backdrop, **windows** (per window, front to back: popups unless raised, decoration elements, masked content, shadow; the stage strip's thumbnails below every other window, with their popups), snap preview, layer-shell top (the menu bar and the dock), **popups** (front to back: those of the layer-shell top, bottom and background surfaces, then those of the key window, each over its own material, outline and shadow; only the key window's are raised (`render::scene::raised_popups_window`), and not while another window covers the output in full screen, so a popup left open in a window behind, such as a tooltip or a popup without a grab, stays below the window in front of it; a menu that opens low on the screen covers the dock, and its material reads the dock below it; an overlay surface keeps its popups directly above it, and the overview keeps each window's popups with its preview), notification banners (and the notification centre list), **input-source HUD**, **accent popup**, the extension layer (nothing draws in it), layer-shell overlay, drag icon, cursor. `LayerStack::flatten` yields the front-to-back list the damage tracker expects. The order is unit-tested (`render::tests`) and checked on a real scene (`tests/headless.rs::element_order_...`).

A full-screen window in front of an output (`Wm::fullscreen_front`) covers its layer-shell top surfaces, the menu bar and surfaces over the whole output aside (the outside-click catchers of the launcher and Control Center, which still take the click that closes their panel): the dock and any other top panel are neither drawn (`render::scene::top_layer_covered`) nor hit by the pointer (`surface_under`) until the window leaves full screen or another window comes in front; the overview shows them. Known limitations: the dock has no bottom-edge reveal in full screen, third-party top panels are hidden the same way, and layer-shell overlay surfaces still draw over the window.

* **Shadows** (`shaders/compositor/shadow.frag`): closed-form Gaussian-blurred rounded box (error function across x, 8-sample integral across y). Parameters come from `cupertino-decorations::ShadowParams` (the verified 32-row table, peak densities 0.40 light / 0.70 dark for active windows) through `ShadowParams::gpu` (`ShadowGpuParams`: σ, vertical offset rounded to device pixels, `ceil(σ·2.8)` reach, density), converted back to points for the shader. Menus use the table's panel row (which class the design uses for menus is unknown). The shadow is cut out under the window shape (`cutout`, approximate design choice). `config::ShadowStyle` remains for the legacy path.
* **Rounded corners** (`clip.frag`): texture shader override on the surface elements (`ClipElement`). Independent of the output transform (winit renders flipped). Corner radius 16 pt for every window style (`cupertino_decorations::WINDOW_CORNER_RADIUS`); while a window enters or leaves full screen the radius is capped at its frame's largest gap to the output's edges (`render::scene::fullscreen_corner_cap`), so the corners round off and back as the frame meets the edges instead of snapping square at the start; continuous corners with the exponent from `cupertino-geometry::CornerStyle` (approximate expansion); the closed-form SDF is the same formula as `RoundedRect::sdf_approx`.
* **Corner policy** (`cupertino-wm` `ToplevelStates::frame_shape`, applied in `render::scene::plan_for`): a zoomed window and one that fills the usable area (the fill tile) keep the rounded corner mask, their title bar and rim when the compositor decorates them, and their shadow, like any window that is not full screen. A full-screen window is square: no corner mask (`WindowPlan::corner` is 0), no decorations and no shadow (the model fades the shadow out over the enter transition), from the start of the enter transition to the start of the exit. The overview and stage placements draw every window, full-screen ones included, with their own rounded corners. A client that said it draws its own decorations (xdg-decoration client-side mode, `WindowEntry::draws_own_frame`) keeps its own shape in every state: the compositor draws no corner mask and no shadow around it. A client that never binds xdg-decoration gets the compositor's mask and shadow like a decorated window (`style_client_decorated`, on), since nothing says it draws a frame of its own.
* **Wallpaper** (`render/wallpaper.rs`): the wallpaper layer draws, per output and appearance, the first image that loads of: the user's `wallpaper` / `wallpaper_dark`, then the asset pack's default picture, then the procedural shader (unchanged). The frame loop never touches the file system and never waits: one worker thread opens, decodes and scales (cover: the longer side cropped evenly, Catmull-Rom, to the output's device pixels, in its logical orientation, so a quarter-turned output gets an upright image) on request, newest request per output wins and older answers are dropped, a file is decoded once however often the output size changes, and the worker looks at the file again every 5 s, decoding again only when its size or modification time changed. The decoded image is kept only while some output asks for its file: when the wallpaper goes back to the procedural one, or an output is not asked about for a minute, it is let go. Until an answer is in, an output keeps what it showed (the procedural wallpaper at the start), and a new image is put up as soon as any output's frame takes the answer in, the output it is for marked for a frame, so an output that is off or locked when its image comes in holds nothing up (frames are wanted only while the worker owes an answer). With each scaled image the worker samples the strip under the menu bar (`strip_samples`: about 16 000 pixels of the top rows of the bar's height in points, from `MenuBarSet::bar_height`, times the scale, rounded up) and measures it, once per image and never per frame. The bar draws nothing of its own over the wallpaper (a solid strip only under Reduce Transparency, when its text keeps the appearance's palette), so the strip is measured as it is (`strip_lightness`: each sample through the colour operations it is given, none for the bar, `cupertino_glass::cpu::apply_color_ops`, then the mean of their CIE L*, in tenths, so a strip of thin bright lines over dark measures dark as the text sees it; the request carries the operations); the frame that puts the image up hands the measure to `set_backdrop_lightness` (*menu bar* above). From the same samples and through the same operations `strip_spread` measures how unevenly light the strip is in 64 bands of equal width across the output (`SPREAD_BANDS`; the standard deviation of their L*, in tenths, so a band half black and half white is 500), which `set_backdrop_spread` sends to bars of shell version 21 as `backdrop_spread` (one little-endian 16-bit value per band, at most 256, again when a band moves by more than 10); the procedural wallpaper is even (every band 0). The scene hands the bar's operations (none) over through `Wallpapers::set_bar_material` only when the appearance or Reduce Transparency changes. Then the kept samples of every image shown are measured again on the compositor thread, about 1 ms each in a release build, and each lightness that changed is handed out without reading the image again; an image read while they changed is measured again as it is put up, and an output with the procedural wallpaper at its next frame. What is kept to hand an output's lightness out once is dropped when nobody has asked about the output for a minute, so an output plugged in again is told its lightness again. The procedural wallpaper is measured by its average colour (`wallpaper_tint`, the materials' tint) through the same operations: its lightness is handed out once for each output and again only when it changes (the appearance or the operations), so the bar is right on the default wallpaper too. The image's pixels are premultiplied, so where an image is transparent it reads as black, at most about 3.5 L* darker than the near-black clear colour that shows there. The file is opened without blocking and checked to be a regular file through the descriptor; only PNG and JPEG up to 256 MB and 8192 px a side (about 0.5 GB of memory at most) are read, and a missing, unreadable or unsupported file is logged once and the next candidate stands in. The average colour of the image tints the materials in place of the procedural wallpaper's. The lock screen and the power fades stay black. A change of the keys in `compositor.json` (the Settings application writes them) applies without a restart.
* **Material pass** (`render/material.rs`, below): backdrops of shell processes (the menu bar strip, the dock bar, the dock process's switcher panel), the launcher panel (a backdrop of the launcher process, recipe of the appearance), the banners, the HUD and the accent popup.
* **Decorations** (`decor.rs`): title bar (fill, rim along the top, separator, window control buttons with glyphs on group hover, centred title with ellipsis) and the inner rim just inside the frame (`Decor::edge`: white, as wide and as strong as the appearance's row of the shadow table says) are rasterised on the CPU (`tiny-skia`, `cosmic-text`) into premultiplied buffers at the output scale. They are cached per window and re-rendered only when width, scale, active state, hover / pressed state, the enabled minimize and zoom buttons, title or appearance changed, and drawn as `MemoryRenderBuffer` elements rescaled with the window.
  * The outline (`SceneKind::Outline`) is a black ring half a point wide just outside the frame of a decorated window, drawn by the rounded-rectangle shader above the shadow and fading with it, so a full-screen window has none; with Increase Contrast it is the `window-rim` token a point wide. The outline lies around the device pixels the window's content and its mask cover, so it meets them at every scale and position. The edge of a popup with a backdrop (glass or material) is the menu edge (`Decor::menu_edge`): its outline (`SceneKind::PopupOutline`) is full along the sides and fades to nothing at the top and bottom, and over glass a white rim half a point wide just inside the shape (`SceneKind::PopupRim`, in front of the glass) is brightest along the top and bottom and fainter along the sides. The shader weights a border by the direction of the shape's outward normal `n` (`RoundedRect::border_falloff`: `floor + (1 − floor) · |n.x|^sides · |n.y|^ends`). The rounded-rectangle element lies on whole device pixels, so a one-pixel line is sharp at every scale.
  * Hit testing (`Hit::{Button, Titlebar, Resize(edge), Content}) runs on the plans of the topmost window first.
  * Buttons act on release over the same button: close sends `RequestClose`, minimize sends `Minimize` towards the dock's slot, zoom sends `ToggleZoom`.
  * A title bar press starts the model move. A double click runs the configured action (zoom by default). Resize zones start `BeginResize` and show the resize cursor.
  * **Input order** (`Cupertino::surface_under`, top down, as drawn): layer-shell overlay surfaces, the popups of the other layer surfaces, the popups of the key window (`window_popup_under`), layer-shell top surfaces, the windows (each with its own popups first), the layer surfaces below. A click on the part of a menu over the dock reaches the menu, and a click on a window in front of another window's popup reaches that window (`tests/popup_over_dock.rs`).
  * **Input order per window** (`Cupertino::window_target_under`, top down, after the key window's popups): the window control buttons of a unified bar, the window's popups (when it is not the key window), the resize zones (3 pt inside to 4 pt outside the frame, corner zones 12 / 15 pt), the client's surface inside the frame, then the title bar and buttons. The resize zones win over the client surface, so the inner band works whatever the client's input region covers. The 4 pt outside part belongs to titled windows only (ours with a title bar, and every client-decorated toplevel, whether or not it draws a header bar, since the server cannot tell); a window of ours without a title bar has the inside band alone. The cursor follows what the frame can do along each axis: the two-way cursor where the edge can grow and shrink, the single arrow where only one way is left (at the minimum width the side edges point outward), and no cursor and no zone where it cannot move, so a fixed-size window (min = max) shows none and its title bar takes the top band (corner rule, `decor::resize_cursor`). The client's size limits reach the window model as frame limits, the insets added (`state::frame_limits`), so an SSD frame is not resized below the client's minimum. A **client-decorated** toplevel gets the same zones from its window geometry and the same compositor-started resize (decision of 2026-10-25); the client's own input region outside the frame (a drawn shadow, GTK's 12 pt) takes no input beyond the band: the pointer passes to what lies below, as the design's shadows are not clickable.
  * **Popup grab** (`popup_grab.rs`): while a client's `xdg_popup.grab` is active, the pointer follows the popup chain of its toplevel (a press on a popup goes to that popup, and a popup that maps or commits under a pointer that does not move takes the pointer focus), a press anywhere else dismisses the whole chain and is consumed (it reaches neither the window nor a shell surface under it; its release is consumed too), and the keyboard stays with the topmost popup until the grab ends, then returns to the toplevel. A layer surface's popups (the menu bar's menus) give it to the exclusive layer surface, else the key window (`keyboard_after_grab`): a layer surface holds the keyboard only while it asks for it, so a press on the bar's empty space while a menu is open closes the menu and leaves the keyboard with the window that had it. A popup that has not committed a buffer cannot be hit, so a press at its place counts as outside. Only the popups of the grabbing toplevel (and their subsurfaces) belong to the chain, so a press on that toplevel itself or on an in-window menu bar of the same client is consumed too (two clicks to switch menus), which xdg-shell allows. A session lock ends the grab. Whenever the keyboard moves outside the grab's chain, the grab ends first and its popups get `popup_done`: one check in `set_keyboard_focus` (`end_popup_grab_for_focus`), the path every move of the keyboard takes, so a window the focus policy picks (`Effect::Focus`), an exclusive or on-demand layer surface (the launcher, Control Center, Focus Dock), the authentication prompt and a lock surface all close the menu of another surface (the dock's, the menu bar's, the launcher's) and get the keyboard straight away, never after the grab's toplevel. The keyboard going to nothing (the key window closed while a shell panel's menu is open) ends the grab as well, as it did before. An on-demand layer surface takes the keyboard only by a press, which a menu's grab treats as a press outside: it closes the menu and is consumed, and the next press gives it the keyboard. Focus given to the grab's toplevel or to a popup of its chain keeps the grab, and a window the focus policy picks while an exclusive layer surface (the launcher) holds the keyboard gets no keyboard, so the layer's menu stays open. A menu is never left open without its keys.
  * **Engaged shell layers** (`state.rs release_engaged_layer`): a dock bar or a menu bar asks for exclusive keyboard interactivity only while it is engaged (Focus Dock, the menu bar's keyboard mode or Help search). A press outside it and its popups ends that before anything else handles the press: the server stops treating it as exclusive, gives the keyboard to the key window (the press then focuses the window under it as usual; a menu open from the layer closes first, the keyboard going back to the layer so that it is told when it leaves, and the press is consumed as any press that closes a menu), and the layer answers `wl_keyboard.leave` by letting go. Until it commits without exclusive interactivity, or is engaged again, its claim is not honoured, so a commit made before it let go does not take the keyboard back. Other exclusive layers (the authentication prompt, the launcher, the dock process's overview) are not released by a press, and nothing changes under the lock, where presses go to the lock surface.
  * **Move and resize requests** (`handlers.rs held_press_on`): `xdg_toplevel.move` and `.resize` start only when the serial is that of the seat's pointer (or touch) grab that is still active and went to a surface of that window; a request made without a held button would otherwise glue the window to the pointer. The serial of a key, focus change or later press that came while the button was held is not that grab's, so it starts nothing either. Others are logged and ignored. `.show_window_menu` is not answered (the server has no window menu), so its serial is not checked.
  * **Hung applications** (`hung.rs`, `frame.rs cursor_choice`): every second the server pings each client that owns a mapped toplevel (shell processes own layer surfaces, not toplevels, and are not pinged); no pong 2 s after the ping marks it unresponsive until it answers. The pointer over the content of one of its windows shows the theme's `wait` cursor (the procedural theme has it), unless a server decoration zone (a resize edge) has its own. Every change is sent to the docks (`cupertino_dock_v1.unresponsive`, and as a snapshot when a dock binds), which show "Not Responding" in the dock menu and the switcher.
  * **Focus on map** (`state.rs map_focus`, `cupertino-wm` `Activation::Policy`): for every toplevel the server tells the model whether it is its client's first (`ClientState.mapped_toplevel`) and its process's first (`Cupertino.mapped_processes`: the process id and `/proc` start time from the socket credentials, `process.rs`; the grant goes once to a process however often it reconnects while a client of it that mapped a toplevel stays connected, is forgotten when the last of those disconnects, and never goes to a process that cannot be named), whether the last key or button press went to another client after this one connected (`Cupertino.last_input`, `ClientState.connected_at`), nothing at all for the first-window grant while the session is locked, the activation token the client presented for the surface (kept in `pending_activations` when the surface is not mapped yet, which is the usual order), else the `XDG_ACTIVATION_TOKEN` its process was started with (`process.rs launch_token`, from `/proc/<pid>/environ`), so a program that never presents the token of its launch (Files, most terminals) still comes forward from the launcher or a dock tile, and the last user event. The rule and its tests are in `cupertino-wm`. Known trade-off: a program started less than 1 s after the last keystroke (for example right after Enter in a terminal) opens behind the key window and its tile bounces; the first-window grant is not given while the person is typing.
  * **Force Quit** (`force_quit.rs`): `Super+Alt+Escape` (`force-quit`) ends in `ShellOp::OpenForceQuit`, which sends every dock `force_quit_dialog`; the dock process draws the dialog and sends `force_quit_app` after the person confirmed. The menu bar's Force Quit <app> (the Alt alternate of Force Quit…, `cupertino_menu_bar_v1.force_quit_app`, version 13) runs the same `force_quit_app` with no dialog, only when its app id equals the key window's application identity (the id `active_app` sends) when the request is handled; another id, an id over `MAX_APPLICATION_ID_BYTES` (255) and every request while the session is locked or a lock is pending are ignored with one log line, never a protocol error. Requests are not de-duplicated: a second one for the same application within `KILL_GRACE` (from the bar or the dock) sends SIGTERM again and queues a second delayed SIGKILL, which ends nothing the first did not. The process is the pidfd the kernel named as the client connected (`SO_PEERPIDFD`, Linux 6.5), so no process id is looked up; a client the kernel named no process for (an older kernel) is not signalled, because the socket credentials are a snapshot from connect time that cannot show a reused process id. The pidfd is held from then on (`pidfd_send_signal` for the SIGTERM and the delayed SIGKILL), so a process id that is reused meanwhile is never signalled. Only application clients are signalled: not the server's own connections or its shell processes (also not their pids), not pid 0 or 1 or the server itself, and not a client that serves windows of more than one application (a proxy). The delayed SIGKILL goes only to clients still connected. An application whose windows belong to a wrapper that forked away from the connecting process has only the connecting process signalled.
  * Moves and resizes the server starts from a press (title bar, resize zones; there is no modifier drag, a modified click reaches the client as on the design) wait in `PendingDrag` until the pointer leaves the 5 pt box around the press (`cupertino_input::drag_started`), then start anchored at the press.
* **Window effects** (`render/mesh.rs`, `fx.rs`): while the model animates a minimize or restore, the window is captured offscreen at its natural size (decorations and content, `capture_window`; a material samples what lies below it, which the clear capture lacks, so its backdrops are drawn as the fallback fill) and drawn through the `cupertino-effects::MinimizeEffect` mesh (warp 500 ms, funnel 400 ms or scale 200 ms; `minimize_effect` in the configuration, `plain` keeps the rescale) towards the rectangle the dock process committed with `set_minimize_target` (global through its layer geometry; no mesh target without a dock). The mesh's dock edge is the screen edge nearest to that rectangle. The effect generators carry their own easing, so the model's minimize / restore curves are set to linear over the durations. Restoring takes the same time as minimizing, the progress running back. The `render::motion` unit tests check that timing for each effect and under Reduce Motion, and the scale's fade.
  * **Closing**: a snapshot of the window with its shadow is stored (throttled to once per 0.5 s per window, on commits and once when the open animation ends) and refreshed live right before an unmapping commit. When the window disappears the snapshot fades out (`WindowClose`, 0.15 s) as a ghost.
  * **Opening** (scale 0.98 → 1 + fade, spring 0.25 s) and zoom come from the model's presentation. Workspace slide positions use `WorkspaceSlide::offset_x`.
  * **Show desktop** (`F11`, four-finger spread, hot corner) moves every window with `ShowDesktop::placement` (spring with damping ratio 1.0 and response 0.3 s) and is reversed by the same action.
* **Menu bar** (`menu_bar.rs`, `cupertino-wm::menu_bar`): a top-anchored layer surface of the menu bar process with the menu-bar role (`get_menu_bar`; one per output). The server owns its frame as the design window server does. The model keeps per output the height reserved in the usable area (the configured `menu_bar_height`, not the client's exclusive zone, and none while the bar is hidden), the inactive output's dimming (opacity lost 0.4, approximate), auto-hide in full screen and the reveal at the top edge (`EdgeReveal`), kept while a menu is open (`set_menu_open`). A full-screen window's title bar, ours whether the window is decorated by the server or by its client, slides in below the revealed bar as one piece with it (`WindowEntry::revealed_titlebar`, `MenuBarSet::fullscreen_titlebar`), across the output with square corners and no rim, standard style whatever the window's (a unified bar is drawn over the client's toolbar, which stays under the menu bar), and drawn over the window's content; its close and zoom buttons act as on a window (the zoom button leaves full screen) and its minimize button is disabled, since a full-screen window does not minimize, the rest of it takes the pointer from the client, and the bar stays revealed while the pointer is on it (the edge reveal's hold region covers both). Not shown when the bar does not auto-hide in full screen. The surface is drawn with that presentation's vertical offset and opacity, and pointer hit-testing follows the offset, so a hidden bar takes no input. The feed (`active_app`, one of `menu_none` / `menu_dbusmenu` / `menu_gtk`, `window_state`, `done`) goes to every bar on bind and whenever the key window, its title, its menu address or its window state changes. Menu addresses come from the appmenu and `gtk_shell1` protocols and from `cupertino_app_menu_v1.set_address` (version 2 of `cupertino_app_effects_v1`), which the server checks for a unique bus name and object paths of at most 512 bytes (so the `menu_gtk` event that carries them fits a message) and announces as a `menu_gtk` address, checked like the others below; destroying the object withdraws it. The appmenu and `gtk_surface1` announcements are held to the same limits: the bus name (unique or well-known) at most 255 bytes, every object path given a D-Bus object path of at most 512 bytes and the `gtk_surface1` application id at most 255 bytes; an announcement that breaks one is not a protocol error (they are not our protocols) but gives the window no menus of that kind, withdrawing any it had: one malformed or overlong path, even an optional one, withdraws the whole address of its kind, and the warning is logged once per surface however often the announcement is repeated. The owner's unique name the bar is sent in place of the announced name must be a unique bus name of at most 255 bytes too, so `menu_gtk` is at most 2608 bytes and `menu_dbusmenu` at most 788 whatever the absent strings (sent as empty ones) and the resolution add. A window keeps one address of each kind, GMenuModel (`gtk_surface1`, `cupertino_app_menu_v1`) and DBusMenu (appmenu), each announced, checked and withdrawn on its own; the bar is told the GMenuModel one whenever it has a menu bar path, in whichever order the two came (the GMenuModel items name their actions, which the bar rebinds by), else the DBusMenu one, else a GMenuModel application menu alone, which does not hide a DBusMenu menu bar. A `gtk_surface1` with a menu bar path, an application menu path or both is an address. A window's addresses, and any announcement of its surface still being checked, go when its toplevel is destroyed. Every `cupertino_app_menu_v1` gets `menu_bar(1)` while a bar runs and `menu_bar(0)` while none does, on creation and when the first bar starts or the last one stops or its output goes. From version 3 `menu_bar(1)` also needs a verified reader, and it also gets `menu_reader` (before `menu_bar(1)`, after `menu_bar(0)`): the unique name of the connection that owns `com.canonical.AppMenu.Registrar` once the owner check (`owner_check.rs`, key `MenuReader`) finds it is the menu bar process, empty otherwise, on creation and whenever it changes. The check runs when the first bar starts and on every `NameOwnerChanged` of the name (a watch on the D-Bus worker); with no bar there is no reader. A refusal for a passing reason (`Busy`, `TimedOut`, `Stalled`) keeps the reader so far and is checked again after 1 s, doubling up to 30 s. A new reader sends every bar its group again, unchanged, so a bar whose load the application refused before it had the reader loads again. A shell connection's process for the check is the one the server started for it (`ClientState::process`). The bar process reads the menus. The bar is told an address from any of the three only once its owner is checked (`owner_check.rs`): the D-Bus worker asks the bus daemon, never the name itself, for the owner of a well-known name (`GetNameOwner`) and for the owner's `GetConnectionCredentials`, and the owner must be the surface's Wayland client or a process of its sandbox instance (`cupertino_peer::same_instance`). The client is held by the pidfd of its socket (`SO_PEERPIDFD`, taken as the connection is accepted) and the owner by the `ProcessFD` the daemon gives; a daemon that gives no `ProcessFD`, an owner or client that cannot be classified, a name nobody owns and a connection the server made itself (no peer process) all mean no menus. On a match the bar gets the address with the owner's unique name, so a later owner of a well-known name cannot take the menus over. Until the check returns, and on a refusal, the window has no menus (`menu_none`); a refusal is logged once as a warning. Each announcement of a surface replaces the one of the same kind before: one check of a surface and kind is on the worker at a time, a newer announcement waits and is checked when it returns, and the older answer is dropped; withdrawing the address or destroying the surface drops the answer. At most 8 checks run on the worker at once and at most 2 of one client; the rest wait in order, so a client announcing many surfaces waits behind its own checks while other clients' run. A check not answered within 3 s is answered as timed out (no menus) and its surface's next announcement goes out; the late answer is dropped. A refusal that may pass, timed out or busy (below), is retried for the same announcement at most three times, 1, 2 and 4 s after each refusal, each retry one more check of the same surface and kind under the same limits; the window has no menus meanwhile, and a newer announcement, a withdrawal or the surface's destruction drops the retry. When the retries run out, one warning is logged (not one per attempt) and the announcement is kept: when its window next becomes the key window it is checked once more, with its three retries counted afresh, so a long stall of the bus does not leave the window without menus until the application restarts. Every other refusal is final. Each identification reads `/proc` on a short-lived thread of its own (a process's root can stall reading for good, and such a thread is left behind), never on the worker that makes the shell calls. At most 16 identification threads are alive, those left behind included; with 16 a check is refused as busy. At most 3 of them belong to one client: while 3 of a client's identifications are alive, its checks are refused at once (one warning when it reaches the limit), and it gets checks again exactly when one ends. The bound is on live threads, so a client that stalls its identifications holds 3 at most however it spaces them or mixes in checks that verify; a check that times out because the bus is slow or suspended starts no thread and costs the client nothing, even when the bus answers it later (a check answered after its deadline starts no identification). What is left: only an unsandboxed process of the same user can make a root that stalls (a Flatpak or Snap sandbox allows no user namespace), and by opening many clients it can still use up the threads and stop the menus for the session; a process with that access can end the menu bar process anyway, so it gains nothing new. The application id and the title in `active_app`, and in the dock's `window` events, every application id the dock is sent (`launching`, `unresponsive`, `attention`, the switcher's entries, the overview's) and the title and application id the foreign toplevel list sends are each cut to 1024 bytes at a character boundary: a client sets them to any length and one message must stay under the wire's 4096 bytes. From version 10 the group also lists the windows of the active application (`app_window`: the dock's window id, the title cut to 1024 bytes at a character boundary, active and minimized flags; top of the stack first, at most 1000), and a group of its own after the first ones and after every change of the key bindings or the modifier profile names the physical chord of each `bound_action` (the chord bound last that the profile can make, in the shortcut file's syntax, empty when none) and the primary modifier (`super` for `cupertino`, `ctrl` for `classic-pc`). `window_command` and `move_to_workspace` run the window-model commands of the fallback menus; version 10 adds full screen (enter or leave), the three tiles (the shortcuts' paths), bring all to front (`Command::BringAllToFront`: the application's windows raised in their order, the focus kept), cascade (the same, then each window behind the key window 24 pt further up and left, kept in the usable area), minimize all, zoom all (each window whose size is not fixed and that is not zoomed) and the force quit dialog (the shortcut's `ShellOp`); an entry above the object's version is `invalid_command`. `activate_window` focuses a window of the active application (unminimizing it and switching to its workspace); any other id, and every request while the session is locked or a lock is pending, is ignored. Version 11 adds `edit`: it counts only while that bar's popup grab is active (the choice is a click in its menu; otherwise it is ignored without an error), and only for a key window that is the xdg toplevel of a public-socket client (an X11 window too, which the satellite shows as one, see *X11 applications*; never a layer, lock or shell surface), with no lock (active or pending), overview, switcher or move or resize under way. One edit is kept (a newer one replaces it); the first keyboard focus change after the grab ends sends it if it gives the keyboard to that window within 500 ms of the arrival (model clock, checked at the tick) and drops it otherwise, and every guard is checked again before sending. The chord comes from `edit_chord` with the client class and opt-out of the keyboard rewrite (`rewrite_terminals`, `rewrite_off`): a terminal gets only copy and paste as Shift+Ctrl, a first-party or opted-out client the profile's primary modifier, any other Ctrl. `forward_chord` (`kbd_filters.rs`) sends it through the rewrite's forwarding: the chord's modifiers, the press and the release of the key that types the letter in the active layout (else the key of the shortcuts' Latin fallback), then the real modifiers; it passes neither the shortcuts nor the rewrite and arms no repeat. When the client destroys the last popup of a layer surface's grab (a bar menu closed on a choice), the grab ends at once and the keyboard goes back to the exclusive layer, else the key window (`popup_grab.rs`). The `focus-menu-bar` action sends `engage` to the bar of the active output (the one under the pointer) and gives its surface the keyboard when its layer accepts it. Version 12 adds `engage_help`: the `help-search` action (Shift+Super+/ under both profiles: the design table's Shift+Primary+/ under `cupertino`, a line of the `classic-pc` table, a proposal, since Ctrl+Shift+/ stays with the applications) sends it in a group of its own to the bar of the active output, only to bars of version 12 or later, and the bar opens its Help menu with the search field focused, taking the keyboard as for `engage`. `focus_help_search` itself sends nothing while the session is locked or a lock is pending, whatever calls it; the shortcut group of a version 12 bar also names the `help_search` chord.
* **Overview** (`shell.rs`, `cupertino-overview::Transition`): the server opens a session on the pointer's output (`Ctrl+Up`, `Ctrl+Down` for the front application, a dock's `run_action` or `app_command`), sends that output's dock the window set (desktop frames), the workspaces and the usable area, and animates every window from its desktop frame (a minimized one from its dock tile) to the frame the dock answers with (`overview_frame`, the reflow spring for a later change) by the transition's progress (0.25 s). Live window textures rescale (same elements as on the desktop) over a dim backdrop (`overview_dim`). The window set is resent when windows open, close or change state, the workspaces when they are added, removed or reordered. The dock's `overview_select` focuses or restores and leaves, `overview_close` leaves, `switch_workspace` leaves then switches. Without a dock, or with a dead or hung one, the server still leaves on Escape, on a click (a window under the pointer is selected, empty space leaves), on any workspace switch (shortcut or swipe) and when the dock's object or surface goes, and puts the windows back. The chrome (workspaces bar, highlight, titles, keyboard navigation) is the dock's alone.
* **Damage tracking**: `OutputDamageTracker` per output. Elements rebuilt every frame get stable ids and commit counters from `ElementCache` (a hash of their parameters), so nothing is damaged unless a parameter changed. Material elements are damaged whenever anything below them changed (their generation is a hash of the (id, commit, geometry) of everything beneath, assigned by `finalize_materials`).
* **Cursor**: xcursor images by name (cursor-shape protocol) from the theme of the first asset pack that has one (`<pack>/cursors/<theme>`, the theme name from the manifest; no host theme and no environment override); without a theme, or with one that lacks `default` and `left_ptr` (reported on stderr), every cursor is the built-in arrow and the clients keep their own theme; with one, the clients the server starts get `XCURSOR_THEME` = that name and `XCURSOR_PATH` = the pack's `cursors/` directory, so they find no other theme; the image is sampled whole at every output scale (a scale-2 output picks the 48 px image for 24 pt, and the element's source rectangle is the full image); built-in arrow fallback, client cursor surfaces, all drawn by the compositor (the host cursor is hidden in the nested window). Server-drawn cursors use the cursor scale: `cursor_size` (1…4) times the shake-to-locate multiplier, from the smallest theme image at least that size. A client cursor surface takes only the shake multiplier, since clients started by the server get `XCURSOR_SIZE` = nominal size × `cursor_size`. `cursor_fill` / `cursor_outline` (default black / white) redraw the theme images by lightness, the drop shadow kept black (approximate). Shake to locate (`cursor.rs`, `cupertino_input::ShakeDetector`): every pointer motion feeds the detector, a recognised shake grows the cursor 5×, and a 1/60 s timer shrinks it back once the shaking stops. The built-in cursors come at 1x, 2x and 4x of the nominal size, each role on its own canvas with its own hotspot (`cupertino-cursor`: the arrow 28 × 40 with its tip at 5, 5, the I-beam 23 × 22 at 12, 11, …); `CursorFrame::hotspot_at` and `size_at` scale both from the image picked for the output's pixels, so the hotspot stays on the pointer's point at every output and cursor scale (`cursor::tests` at 1, 1.5 and 2). The cursor is a `Kind::Cursor` element and the DRM outputs allow cursor-plane scanout, so where the hardware's cursor plane fits the image a pointer move is a plane update; otherwise the server composes a frame from the buffers the clients last committed. Either way no client's frame holds a pointer move up.

### Material pass and the GLES shader port

`render/material.rs` runs inside `MaterialElement::draw` on the renderer's context (`GlesFrame::with_context`), with the target framebuffer bound, and restores every piece of GL state it touches:

1. capture: of the bound framebuffer into a half-size texture (linear filter = 2x2 box average; RGBA16F when renderable, else RGBA8),
2. downsample pyramid (`downsample.frag`) while σ² > 64 texels²,
3. separable Gaussian (`blur.frag`),
4. colour operations (`color.frag`: luminance curve, saturation, monochrome, and the display filter's linear matrix, invert and contrast),
5. composite (`material.vert/frag`): SDF mask, backdrop sample, fill layers with their blend modes, drawn once per damage rectangle with the blend state (SRC_ALPHA, ONE_MINUS_SRC_ALPHA) / (ZERO, ONE).

Recipes come from `cupertino-theme` (`MenuBar` for the strip, `Menu` for the dock bar, and `Switcher`, the switcher panel's code recipe of, for the dock process's panel) through the `cupertino-glass` encoders (`ops`, `blur::plan_blur`); uniform blocks are the std140 structs of `cupertino-glass::ops` unchanged. The shaders in `shaders/` are copies of `cupertino-glass/shaders/gles/`; `color.frag` is kept identical to its original.

**Check against the CPU reference.** The ported shaders compiled and linked unchanged on GLES 3.2 (NVIDIA 615.78) and produce the design result; no shader needed a bug fix. `tests/shell_v1.rs::backdrop_material_pass_matches_the_cpu_reference` renders a backdrop strip over the procedural wallpaper and compares it with `cupertino_glass::cpu::render_regions`:

| recipe | mean abs difference (8-bit) | max |
|---|---|---|
| MenuBar light | 0.322 | 1 |
| MenuBar dark | 0.156 | 1 |
| Sidebar light (fills, darken blend, tint layer) | 0.016 | 1 |
| Menu dark | 0.059 | 1 |

**Changes to the copies** (integration only):

* `material.vert`: the quad corners come from a `u_quad` uniform (output pixels, one draw per damage rectangle) and are mapped through `u_proj` (the frame's projection matrix) instead of dividing by the target size, so the output transform (flipped nested framebuffer, rotated outputs) is honoured; a new varying `v_uv` carries the matching framebuffer-normalised coordinate.
* `material.frag`: the backdrop is sampled with `v_uv` instead of `v_px / size` plus the optional row flip (`Region.info.z` is unused), and the `u_source` branch was removed: recipes without a backdrop filter use an unfiltered full-size copy of the framebuffer as backdrop (the capture pass runs with no pyramid).
* The `Region` / `PassParams` blocks are unchanged; the Smithay renderer exposes no UBOs, so all passes use raw GL through `with_context`.

announcements before the window maps are applied at map time) and **`gtk_shell1` / `gtk_surface1`** (`set_dbus_properties` → GMenuModel address, checked the same way; `present` / `request_focus` focus the window; the protocol is generated from `protocols/gtk-shell.xml`, a wire description of the interface; `capabilities` is `global_menu_bar` while a menu bar exists and 0 once the last one goes, sent on bind and on every change, so a GTK window hides its own menu bar only while the bar shows its menus). `zwp_text_input_manager_v3` and `zwp_input_method_manager_v2` are exported **only when an accent table is configured**: the input-method global is restricted to the compositor's own in-process client (the accent bridge, see *Keyboard*), so an installed input method keeps the seat's single slot otherwise. **`ext-image-capture-source-v1`** (output and foreign-toplevel sources), **`ext-image-copy-capture-v1`** and the private **`cupertino_screenshot_v1`** are offered only to *privileged* clients (see *Screenshots*); a client of the public socket does not see them, so an application cannot read the screen. While a copy session runs (not stopped), menu bars of version 3 get `screen_capture 1` in a group of their own, and `0` when the last one ends; the bar shows the screen capture indicator. Camera, microphone and system-audio indicators need the PipeWire graph, which the server does not read (no C library): not shown. **`wp_linux_drm_syncobj_manager_v1`** (explicit sync) is offered on the TTY backend when the kernel can wait on syncobj timelines (`DRM_IOCTL_SYNCOBJ_EVENTFD`, Linux 6.6 and later; the log says whether it is offered): a commit that carries an acquire point is held back until the point is signalled, and the release point is signalled when the compositor drops its last handle of the buffer. A frame drawn from client buffers holds the buffers of every surface tree it drew (subsurfaces included, `frame::drawn_buffers`) until its flip is done, which the kernel waits on the render to finish for, so a buffer the GPU composited is released only after the GPU read it, not when the client commits the next one (a buffer scanned out directly is held by Smithay until the flip after it). Known limits: a frame that is drawn but not queued (the queue refused) lets its buffers go at once, and a buffer drawn only into a screenshot or capture is released when it is read back, as before. A window snapshot (`capture_snapshot`, for the close and minimize effects) holds no buffers: a client that commits again right after it may reuse a dmabuf the snapshot pass is still reading, so the snapshot can show part of the next content. Each held commit is an event source with descriptors of its own (`acquire_waits.rs`), counted per client and by what it waits for: explicit-sync acquire points, which a client may never signal, are limited to 64 at once and the client is disconnected with a `wl_display.error` `implementation` at the next one; the implicit fences of any other dmabuf always signal (the kernel times a GPU job out), so their bound is 1024 and past it a commit goes through without waiting, with one warning per client in the log. The sources of a client that disconnected are removed on the next tick. A commit that cannot be held back (no eventfd, no loop slot) goes through unblocked and is logged at warn with the client. At start the soft limit on open files is raised to the hard limit (`file_limit.rs`; both values are in the log); every program the server starts (applications, shell processes, the screenshot process) gets the old soft limit back before it runs, since a program that uses `select` breaks at descriptor 1024 and above. **`xdg_toplevel_icon_manager_v1`** (`toplevel_icon.rs`): the icon a window sets is copied once, at the commit that applies it, so no client buffer is kept or read later: the name only as an icon-theme key (dropped when empty, over 255 bytes, or holding `/`, `..` or NUL), and the largest square ARGB8888 or XRGB8888 `wl_shm` image of at most 512 pixels a side, read through smithay's shm access; docks of shell version 17 get it as `window_icon`.

**Session lock.** The `lock` shortcut action makes the D-Bus worker call `LockNow` (no arguments; the display-sleep lock calls `Lock`, which differs only in the lock screen's idle hide: 5 s after a lock the person asked for, 30 s otherwise) on `org.cupertino.Login1` at `/org/cupertino/Login1`. The login process answers by taking `ext_session_lock_v1`. Only a connection with the SessionLock role (the login process, *Shell roles*) can take the lock. From the request on, the compositor draws only the lock surface of each output over solid black (no windows, layer surfaces, drag icon or overlays), delivers the pointer and the keyboard only to lock surfaces and ends running grabs and drags. Every shortcut, hot corner and gesture is off except VT switching. Screen capture sessions go on, copying an output as black and holding window frames until the unlock (*Screenshots*). `locked` is sent once every output has presented such a frame and has a committed lock surface. On the TTY backend a frame counts as presented only at the vblank of a frame this session queued; a vblank whose frame was dropped with its output's state (sleep, resume) confirms nothing. After one second without surfaces it is sent with black outputs (approximate). Lock surfaces are configured to the output's logical size.

* A second `lock` while the session is locked or being locked gets `finished`.
* If the lock client disconnects, the session stays locked and black until another client takes the lock (`session locked` is logged again). A client that disappears before `locked` was sent cancels the request, unless the system went to sleep meanwhile (below).
* **Activation.** While the session is locked or about to be, no toplevel is activated: every `xdg_toplevel` is configured without `activated` (`Cupertino::activated_window` is none), and a window that maps behind the lock is not activated either. At the unlock the window that was active when the lock began is activated again, and given the focus back if a window that opened behind the lock took it in the model.
* **Sleep cover.** The server holds a logind `sleep` delay inhibitor of its own (`power.rs`). At `PrepareForSleep(true)` (`Cupertino::system_going_to_sleep`), in a session with a lock screen (a shell process with the SessionLock role; never the login screen's server, nor a nested run without a login process, where nothing would take the cover over), a session that is not locked yet, because the lock client hung or crashed before it asked, is covered at once: black on every output, no input to any client, every toplevel deactivated, and the session's observers told it is locked, as after a lock client that disconnected (`Orphaned`), so the next lock client (the login process, restarted or late) takes it over; the lock screen is asked to lock, as the lock shortcut asks it. A lock still pending then stays in force should its client go before it confirms. The inhibitor is released once every output has presented a covered frame (lock surfaces over black, or black; `Cupertino::sleep_covered`), or at once while nothing reaches the screens (the TTY session paused, the display asleep); an output powered off is never drawn and counts as covered. The inhibitor is taken again after the wake, and a `PrepareForSleep` that does not come from the current owner of `org.freedesktop.login1` is ignored (a peer can send one straight to the connection; the owner is followed through `cupertino_peer::signal::from_owner`, with no bus call per signal). Logind's own delay limit (`InhibitDelayMaxSec`) bounds the wait. Logs: `the system goes to sleep before the session is locked: ...` (warn), `the session is covered: the system may sleep` (info).
* Logs: `session locked`, `session unlocked` (info), the disconnect cases (warn).
* Smithay's `unlock` callback does not say which lock object sent `unlock_and_destroy` and also fires for a lock that was refused. The compositor honours it only when the lock object of the current owner is the one that died with the request and the owner's client is still connected. A refused lock's unlock arriving together with the owner's crash leaves the session locked.

### Clipboard

`clipboard.rs` keeps the clipboard when the client that copied exits. When a Wayland client sets the clipboard selection, the server reads the offered types it keeps, one after the other, into memory: UTF-8 text once (the first offered of `text/plain;charset=utf-8`, `UTF8_STRING`, `text/plain`, `TEXT`), then `text/uri-list`, `text/html`, `text/rtf`, `text/tab-separated-values`, `image/png`, `image/tiff`, `application/pdf`, and Latin-1 `STRING` only without UTF-8 text (the Wayland side of the design's pasteboard type table, §7, mapping ). Other types (private formats) are not kept. All types together are capped at `CAPTURE_LIMIT` = 64 MiB (approximate: no limit is known); a type that would pass it is dropped, the ones before it stay. The client stays the owner and serves every paste while it runs. Once it has disconnected (checked after each dispatch of the clients), the copy becomes a server-side selection (its `Snapshot`) offering the text under all four UTF-8 names and every other kept type under its own; pastes are written from memory without blocking the loop. A selection the client cleared before exiting stays empty; the primary selection is not kept (it belongs to its owner by convention; the design has none).

The owner is the client with keyboard focus when the selection is set, which `wl_data_device` requires. A clipboard manager sets the selection through data control without focus; its selection is attributed to the focused client, and the copy takes over if that client exits first (same content; the manager sees its source cancelled). A type still being read when the owner disconnects is incomplete and is not offered; a client that dies in the middle of writing a type and whose end-of-file is seen before its disconnect leaves that type truncated (the two arrive in the same loop iteration in either order). Data control is offered to every client: the server has no sandbox identity (security-context) to deny it to.

Drag and drop between clients is Smithay's `wl_data_device` grab; `tests/drag-and-drop.rs` drags text from one client's window into another's and checks the offered type, the dropped bytes and the source's events. The source gets no `wl_data_source.target` event (Smithay 0.7 does not send it), so a client cannot tell from it whether the window under the pointer would accept the drop.

A client's drag that ends without a drop keeps its icon a moment longer (`drag_return.rs`). That is a drag released where nothing takes it, one its target refuses, and one cancelled with Escape: while a client's drag from a pointer press runs, the server takes Escape (the focused client never sees the key), moves the drag off whatever it was over, so the target hears it leave and is given nothing, and ends the grab, so the source hears `cancelled`. As such a drag ends the server renders the icon surface into a snapshot, before the client lets the surface go, and draws that snapshot in the drag icon's layer, flying from where it was let go to where the drag started over `DRAG_RETURN_DURATION` (0.4 s, easing out), then gone. Where the drag started is the press that began it, kept relative to the frame of the window it was in, so the icon goes to where that point of the window is when the drag ends. When the surface the drag started from is gone, or its window is closed, unmapped, minimized or on another workspace, there is nothing to go back to and the snapshot fades out where it was let go over `DRAG_FADE_DURATION` (0.25 s). A drag that drops loses its icon at once, as before. `tests/drag-and-drop.rs` checks the return after a refused drop, Escape over a target that had taken the drag (no drop, the icon flies back) and the fade after the source's window closed; `drag_return::tests` the placement over time. Limits: the server knows the window a drag started in, not the item in it, so the icon returns to the point of the press even when the application has since scrolled or removed what was dragged; a drag started by touch returns nothing (its icon goes at once); the snapshot is taken at the scale of the output under the pointer.

### Displays

Every backend reports its displays as **heads** (`displays/mod.rs`): the nested window (one head, `winit`, that cannot be disabled, rotated or given another mode; resizing the window replaces its only mode), each connected DRM connector (named `DP-1`, `HDMI-A-1`, ...; make, model and serial from the EDID, the connector's modes with the preferred one first; refresh in millihertz from the pixel clock and totals), and each offscreen display of the headless backend (any size is a mode). An enabled head has an output (`wl_output` global, model output, layer maps); a disabled one has none but stays listed.

An output exists, and its `wl_output` global is announced, only once its backend shows it (`prepare_head_output`, then `create_head_output` after the modeset): a display that fails to turn on, or turns on in a fallback mode after failed tries, announces nothing in between. An output that goes away first closes its layer surfaces (`drop_head_output`), then leaves its layer map without them (`release_output_layers`): a popup grab of one of them ends and an exclusive one gives the keyboard back to the key window, so a panel open on an unplugged display (the control panel) keeps neither the keyboard nor the pointer while its client destroys it. An output that goes away is withdrawn from the clients at once, but its global stays bindable for `state::RETIRED_GLOBAL_LIFETIME` (5 s) before it is destroyed, so a client that binds it before it reads the removal is not disconnected.

A head starts in the state stored for it, else at its preferred mode, the scale of `cupertino_displays::default_choice` for its pixel and physical size and its connector (a built-in panel, `eDP`, `LVDS` or `DSI`, starts at its default size; 1 when the size is unknown) and to the right of the other heads; `--scale` beats both. A stored mode the display no longer offers falls back to the preferred one. A display stored as off is turned on when no other display is on, and when the last display that is on goes away, the first remaining one is turned on.

A display that cannot show the mode it starts in (a link or a dock too slow for it, a mode test the driver refuses) is turned on in the first mode of `displays::fallback_modes` it can show: its size at lower refresh rates, then smaller sizes, each from its highest refresh rate, never larger or faster than the mode it wanted; with none it stays off and is logged. A failure no mode can fix is not retried in other modes: the device busy or not ours (`EBUSY`, `EACCES`, `EPERM`, a paused session); the display stays off with that error. A fallback is announced as the current mode but not stored: the file keeps the mode the display wanted, and the next plug tries it again, until the person gives that display another mode. Only a display the backend turns on falls back; a configuration a client applies that the display cannot show fails and is restored, as before.

**Connectors on the TTY** (`backend/udev.rs`): each scan compares the heads with every connector the DRM scanner maps to a CRTC, not only with the connectors that changed: a connector that waited for a CRTC (more displays than the GPU can drive; logged once) is brought up when another display is unplugged, and a connector whose EDID changed (another display plugged in its place) is connected afresh. A scan runs on every DRM change uevent of the GPU, when the session becomes active again, when the system wakes from sleep and when the uevent queue overflowed; a paused session does not scan. Known limits: the fallback follows a failed initialisation of the output (the driver's test of the first modeset), not a mode that passes the test and then fails its first page flip, which stays black and logs `queueing the frame failed`; which CRTC a waiting connector gets is the scanner's choice (the first free one its encoders allow); a display whose EDID cannot be read during a scan counts as the same display; all of this is tested with the offscreen backend and on the scanner's mapping, not yet on real hardware with more displays than CRTCs.

**More than one GPU** (`backend/udev.rs`, `backend/copy.rs`): every DRM card is opened, each with its own renderer, DRM output manager and scanner, and the heads of each are its own; a uevent goes to the card its device number names, a card plugged in is opened and scanned, and a card that goes away takes its displays with it. One card renders every frame: `CUPERTINO_DRM_DEVICE` (a `/dev/dri/cardN` or `/dev/dri/renderDN` path, or a `/dev/dri/by-path` link to one), else the primary one (the card the firmware booted on, else the first); a value that names no GPU is logged and the primary one renders, and an empty one counts as unset. A render card whose EGL device is a software one (llvmpipe) gives way to the first other card with a render node that opens with a hardware renderer; with none, it renders in software (`src/software_render.rs`): a warning naming the card and a `session.log` line (`<time> only a software renderer is available: gpu=<card>; the CPU draws the desktop`), which `cupertino-diagnose` reports as `gpu.renderer`. A card named by `CUPERTINO_DRM_DEVICE` renders even in software. Checked once in the `ci/vm` guest on a virtio-gpu without 3D: the desktop and its test windows reached the display at 82 frames per second. The connectors of every other card are named after it (`card1-HDMI-A-1`), so two cards' `DP-1` are told apart. A display of another card shows a copy: the render GPU draws the scene, as for its own displays, into a linear buffer of its own, and the display's card imports it as a texture and draws it in its own frame, waiting on the render's sync point there (a GPU wait where the drivers share fences). That way is taken only where the render GPU lists linear buffers to draw into and the display's card lists them to import. Otherwise (the proprietary NVIDIA driver, a display-only card), or when drawing or the import fails (logged once), the render GPU draws the display's frames into a texture of its own, read back into memory and uploaded to the display's card; never into a GBM buffer, as drawing the scene into one made every later offscreen render of the render GPU (screenshots, captures) black on virtio-gpu (virgl); when that fails too, the display is unsupported: logged once and turned off while it stays connected, and stored as on (unless the person turns it on or off), so plugged in again it is tried again. Known limits: client buffers are never scanned out directly on another card's display, and its frame is copied whole when anything changed; the memory path reads and uploads only the rows the frame changed, across the whole width (the whole frame for the first frame and after its texture is new), measured once at 3840x2160 on an RTX 3060 with both sides on that GPU at 7.4 ms for a whole frame, 0.5 ms for 120 rows and 0.2 ms for 24; the uevent removing the render GPU is logged, not survived; the memory path is checked in QEMU (row 344's harness: a virgl render GPU and a display-only virtio-gpu, the copy matching the primary displays across plug, VT switch and suspend); the import path is not tested anywhere yet (neither machine lists linear buffers on both sides), nor whether drawing into its linear buffer has the virgl problem of the memory path's earlier GBM buffers, and nothing yet on real two-GPU hardware.

**No GL fences** (`backend::gles_renderer`): the TTY and offscreen renderers are built without Smithay's `Fencing` capability. Each owns one unshared EGL context, where GL runs commands in order, so a fence orders nothing; and the NVIDIA driver (615.78.08) keeps about 12 bytes for every fence ever created, deleted or not, so a fence per texture upload and per drawn texture grew the server by 0.1 to 0.3 MB a minute without end in the headless soak. Known limits: Smithay still ends every frame drawn into a texture with a fence, which on the offscreen backend is one per output and frame; the nested winit backend keeps Smithay's own renderer, with fences.

**`displays.conf`** (`cupertino_defaults::displays`; `$XDG_CONFIG_HOME/cupertino/displays.conf`, or `CUPERTINO_DISPLAYS_CONFIG`) keeps one section per display, keyed by make, model and serial (by connector name without a serial): `enabled`, `mode`, `position`, `scale`, `transform`. The TTY session reads it at start and writes it whenever a configuration is applied, keeping the sections of absent displays, so a display gets its arrangement back when it is plugged in again. Nested and offscreen runs keep it in memory only. A file that cannot be read stops the start; a malformed section is logged and ignored.

**Output management** (`management.rs`, `zwlr_output_manager_v1` version 4): each bound manager is sent every head with its name, description, physical size, modes, make / model / serial, enabled state, current mode, position, transform and scale, and adaptive sync as disabled; changes follow as they happen, then `done` with a serial that moves on with every change. A configuration must name every head (else the `unconfigured_head` error); one made against an old serial is `cancelled`; one the backend cannot carry out (disabling the last display that is on, a mode the head does not offer, a rotation of the nested window, adaptive sync) `failed`. `test` checks without applying. A configuration is checked as one arrangement first (`cupertino_displays::arrangement::check`): a display stays on, every display that is on lies in the coordinate range and none overlaps another (displays may touch along an edge; there is no mirroring, so two displays on the same points `failed`). Applying turns the heads that go off off first, then brings the others to their state (mode switch through the backend, then position, scale and transform of the output, so windows, layer surfaces, the menu bar and the lock surface follow); a failure part way restores the whole previous state, the offered modes included, and nothing is stored. Disabling a head closes its layer surfaces. A display that comes back to a stored place another display has taken meanwhile goes right of the others instead (`arrangement::free_place`).

**A display that goes, and comes back** (`recovery.rs`). Unplugging a display and turning it off are the same for what it showed. Its windows move to the first remaining output, every frame they can go back to (normal, zoomed, tiled) fitted into its usable area; a full-screen window leaves full screen there (`cupertino-wm`). The pointer comes onto the nearest point of the nearest remaining output, as a motion, so a window being dragged goes on following it. A menu or popup of a window on the display closes (its grab ends), an overview open on it ends at once (one open on another output takes the arriving windows), and while the session is locked the keyboard goes to a remaining lock surface; a display with no lock surface left shows the locked black, never the windows. Restore policy: each window that moved is remembered with the display's identity (connector, make, model and serial, the `displays.conf` key) and its frame there; when a display with that identity comes back, a window still where it was put (same output, same normal frame) goes back to it at the same distance from its top-left corner, fitted into its usable area. A window moved, resized or put elsewhere meanwhile stays, and one that left full screen comes back as a normal window. A resize in progress on the display ends there, with the frame the window was given on the remaining one. When the last display goes, its windows wait without an output and the next display that comes takes them, fitted into its usable area; when their own display comes later they go back to it as above.

**Active output and scales** (`placement.rs`). The active output is the one the pointer last moved onto or the keyboard last went to (the output of the window that took it), whichever came last; its menu bar is the bright one. New windows, layer surfaces created without an output (the launcher, notifications, the control panel), the overview shortcut, the switcher's panel, the Focus Dock shortcut and workspace actions use it; the dock and the menu bars stay per output. A layer surface is told its own output's scale, a lock surface the scale of the output it covers, and a new surface asking for its scale gets its window's, its layer's or the active output's, so no panel draws at another output's scale. Each output keeps its own work area.

**Outputs a surface is on, and the scale of a window across two of them** (`surface_output.rs`). A window shown on screen is on every output its frame overlaps: its surface, subsurfaces and popups get `wl_surface.enter` for each and `leave` for the others, worked out again whenever the window model changes (a window maps, moves, resizes, changes workspace or output, is minimized or restored) and when an output comes, goes or changes scale, so every surface on an output that goes is told it left. A window that is not shown (minimized, of a hidden application, on a workspace not on screen) is on no output. A layer surface, with its subsurfaces and popups, is on its own output; a lock surface on the one it covers. Popups and subsurfaces follow their window wherever they reach. A window draws at the scale of one output, its *scale output*: the one its frame overlaps most. Rule for a window that spans two outputs: another output takes over only once its overlap exceeds the current one's by 10 % of the window's area (`SCALE_SWITCH_MARGIN`), or the window no longer overlaps the current one, or a move or resize of the window ends (then the largest overlap wins as it is); so a window dragged across a seam changes scale once per crossing, past the middle, and never back and forth while it is held near it. Equal overlaps go to the first output in the server's order; a window off every output keeps its scale output, else takes the output the window model has it on. The scale is sent exactly through `wp_fractional_scale_v1` and, to a `wl_surface` of version 6 (`wl_compositor` is offered at version 6), as `preferred_buffer_scale`, rounded up so a buffer never has fewer pixels than the output shows (1.25 and 1.5 ask for 2), with `preferred_buffer_transform` the scale output's transform; each is sent only when it changes, and a client of an older `wl_compositor` gets neither. Before its window is placed, a new surface is asked for the scale its window opens at and is on no output. X11 windows come through `xwayland-satellite` as ordinary windows of one client, so each is told its own outputs the same way. A client's cursor surface, while it is the cursor shown, and a drag icon are drawn on every output they overlap: they are on each of them and draw at the scale of the output under the pointer (worked out at every tick, sent only when it changes); a cursor surface no longer shown (another cursor, a server cursor, the pointer left the client) and a drag icon whose drag ended are on no output. An input method's popup is on the outputs the text cursor of its text input overlaps, at the scale of the one it overlaps most (the key window's while the text cursor is not known), and on none once dismissed. When an output goes, every surface on it is told `leave` before its `wl_output` global is withdrawn. Decisions: a window across a seam is drawn only on the output the window model has it on, yet is told it is on every output it overlaps, so a client may hear it is on an output that shows none of it; the server does not draw an input method's popup (it draws the accent picker itself), yet the popup is told the output of the text it belongs to, so it would draw at the right scale.

**Sandboxed clients.** `wp_security_context_v1` lets a sandbox manager (a Flatpak runtime) open a listening socket for an application; every connection accepted on it is marked `sandboxed` in its `ClientState`, and a client with a context cannot create another one. `authorization::unsandboxed` is the one predicate behind the filters of `zwlr_layer_shell_v1` and the foreign toplevel list, and the `can_view` of `zwlr_output_manager_v1` and `zwlr_output_power_manager_v1`: a sandboxed client does not see them, so it cannot draw a panel or overlay on a layer, list the windows of other applications, reconfigure or fingerprint the displays, or blank them. Clients outside a sandbox keep them (`kanshi`, `wlr-randr`, `swayidle`). Data control asks for more (*Data control*). While the session is locked, `zwlr_output_manager_v1` is `finished` at once (a configuration made before the lock `failed`) and output power stays available. Selections are left alone by a lock and an unlock: the clipboard and the primary selection stay with their owners, byte for byte. A selection set while the session is locked, by anyone (a clipboard manager, or the lock screen, the only client with keyboard focus), is refused: its source is cancelled, the clipboard goes back to the server's copy of what it was and the primary selection is cleared. A clear is not refused (a password tool's timed clear must not leave the password behind): the selection is emptied, the server's copy with it. A read of a selection, or of a drag's data, by any client but the lock screen is refused while locked (the client's pipe is closed empty), also when the client released its seat; a drag held when the lock comes is ended by it and its target reads nothing. Limits: clipboard managers can still read the selections while the session is locked; a refused set of the clipboard whose owner has no complete server copy (over 64 MiB, still being read, or set by a data-control client) clears the clipboard instead, and a refused set replaces the owner's live source with the server's copy; a refused set is seen by other data-control devices for a moment before it is put back.

**Data control** (`data_control.rs`). `ext_data_control_manager_v1` and `zwlr_data_control_manager_v1` read every selection as it is set and replace it without focus, so they are offered only to a connection holding the data control role (the `clipboard` role of a `"shell"` entry, an installed program) and to an application the person allowed in `data-control.conf` (`cupertino_defaults::data_control`, written by the settings application). The rule is the globals' filter, which wayland-server applies where it lists them and where it binds them: a refused client neither sees them nor binds them by a name it learnt elsewhere. An application is the process the kernel named as it connected (`SO_PEERPIDFD`). It must not be sandboxed: a client of a security context is refused whatever it runs, as is a Flatpak or Snap process. Its executable, read through `/proc` while the pidfd shows the process still running, must be the path of an entry and must not be an interpreter, a dynamic loader or a Wayland proxy (`cupertino_defaults::data_control::refusal`: allowing one would allow every script or client behind it). A pinned entry must match the running file's device, inode, size and modification time. An entry without a pin holds only for a file only root can change in directories only root can change, up to `/` (`cupertino_defaults::system::only_root_can_change`), and that file must be the running one. A program replaced since it started runs from a deleted file and matches nothing until it restarts. A client without a pidfd (Linux before 6.5) is refused. The file is read at start and on every change of its contents. A file that is a link, is not the user's, is writable by a group or other users, or is in a directory a group or other users can write allows nothing (logged). A bad line allows nothing and is logged; the rest of the file holds. After each change every client that was offered the globals is judged again, and one that is no longer allowed is disconnected (`implementation` error), since the protocol has no way to end its objects. A client allowed by a change sees the globals once it connects again.

Threat model: the file is the user's, so any unsandboxed program of that user can add itself to it, or load itself into an allowed program (`LD_PRELOAD`). The list keeps the clipboard from applications that do not set out to get it, makes each grant visible and revocable in the settings application, and refuses every sandboxed application. It does not hold against code of the user's own account that sets out to grant itself access: that code can already read the user's files. The sandbox is the boundary. Limits: the watch reports changes of the contents, so a file that only had its mode or owner changed is judged again at its next change or at the next start. Only interpreters and proxies that the fixed list names by file name are refused. A path that holds `#` cannot be an entry. Refusals are logged at debug level, with the program's path only.

**Output power** (`power.rs`, `zwlr_output_power_manager_v1`): `off` blanks the output (the TTY backend clears the CRTC) and stops drawing it; `on` draws it again. An output that goes away fails its power objects.

### Scale and colour

An output keeps four quantities apart (`Cupertino::output_geometry`, `cupertino_displays::OutputGeometry`): the mode in panel pixels, the logical extent in points (the turned mode over the scale, rounded; `output_rect`), the effective scale, and the rasters of buffers drawn for it (a client's buffer is its points at the scale it is told, in 120ths, halves rounded up). `output_pixels_to_global` maps a position in the output's panel pixels to the global logical space by the same scale the output is drawn with; the input path can use it for pointers that report pixels. A scale that leaves less than a point, or is not a finite number above zero, is refused and changes nothing. A scale an output configuration sends (in 256ths, which a client may round or truncate) less than a step from one of the display's "looks like" choices is that choice's exact scale (`displays::exact_choice_scale`), so the desktop has exactly the points the choice names. `OutputEntry::scale_generation` counts the scale changes of an output: whatever keeps something made for the old scale compares it. A size whose scale is not a whole number of 120ths (every built-in size but the default and the unscaled one: 3024 / 1024 is sent as 354/120) gives clients buffers a few pixels off the panel (3021 instead of 3024 pixels for 1024 points, about 0.1 %), which the compositor stretches to the exact points; its own drawing (decorations, shell, materials) uses the exact scale. The protocol's 120ths cannot express it, so this is not avoidable while the output keeps exactly the points the size names. Tested in `tests/output_scale.rs` (one window through eight scale changes: the output's logical extent, the window's unchanged frame in points, the scale the window is told, its buffer and the pixel-point mapping; refused scales) and `displays::tests`.

What depends on the scale or the colours, and what refreshes it. There is no colour management: everything is sRGB, and the colour inputs are the appearance (light, dark, Increase Contrast), Reduce Transparency, the cursor colours and the display colour filter.

| Cache | Keyed by / refreshed on a scale change | On a colour change |
|---|---|---|
| title bar and rim rasters (`decor.rs`, one per window) | width, height, scale, active, hover and pressed state, the enabled minimize and zoom buttons, style, title | `set_appearance` drops them all |
| decoration and overlay glyph masks (`cupertino-decorations` `TextRenderer`) | the pixel size (`set_scale` before every draw), weight, optical size, subpixel position | the stem dilation of the fill colour is in the key |
| overlay images (`render/image.rs`: the volume and brightness overlay, the accent popup, the shortcut notice) | a signature with the scale | and the appearance; unused ones go at the end of a frame |
| cursor images (`cursor.rs`) | every size of the theme kept; the size drawn is chosen each frame from the cursor size, cursor scale and output scale; each animation frame of each size has its own buffer | `set_colors` drops them |
| glass textures (`render/glass.rs`, `GlassCache`) | a signature with the scale and the capture rectangle in pixels | the glass mode (appearance, accessibility options) and fill are in the signature |
| material backdrops (`render/material.rs`) and the display filter | recipe, output pixels, scale, owner | the recipe's colour operations are in the key |
| material recipes (`RecipeCache`) | not scale-dependent | material, appearance, Reduce Transparency, inactive |
| wallpaper (`render/wallpaper.rs`) | output pixels | the light and dark pictures are chosen per appearance |
| element ids (`ElementCache`) and damage | `configure_output` makes a new damage tracker: a full repaint | signatures change |
| closing-window snapshots (`fx.rs`) | not refreshed: a snapshot taken just before a scale change is resampled for the half second it shows | no |

The apps refresh theirs on `wp_fractional_scale_v1.preferred_scale` (`cupertino-wayland-client` reports `Event::ScaleChanged`; the toolkit then drops its paint and layout caches and repaints in full): glyph rasters are keyed by their pixel size and fill luminance, icon renditions by their pixel size and colour, buffers by their pixel layout, and a cursor the client draws follows the scale of the surface under it.

### Session bus

`dbus.rs` runs one worker thread (feature `dbus`, on by default; `CUPERTINO_NO_DBUS=1` disables it). It starts on the nested and TTY backends, and with `--dbus` on headless. `DbusHandle::shell_calls()` tells how many calls on shell processes were queued and how many the worker is done with (made and answered, refused or failed, with what follows), so a test waits on the worker rather than for a while.

* `ToggleCentre` on `org.cupertino.NotificationCenter1` (the notification process);
* `Toggle` and `ToggleApplications` on `org.cupertino.Launcher1` at `/org/cupertino/Launcher1` (the launcher process) and `Toggle` on `org.cupertino.ControlPanel1`;
* the media key steps of `org.cupertino.Osd1`;
* `Lock`, `LockNow`, `RequestLogOut`, `RequestPowerDialog` and `PowerKey(pressed: b)` on `org.cupertino.Login1`. The `lock` action is bound by default to `Super+Ctrl+q`, the `logout` shortcut name (server action `log-out`: the confirmation panel, the applications quit first; it no longer ends the server) to `Super+Shift+q`, the `power-dialog` action (the power panel: Restart, Sleep, Cancel, Shut Down) to `Ctrl+XF86PowerOff` and `Ctrl+XF86Eject`, and the `power-key` action to the power key `XF86PowerOff`. `Ctrl+Alt+BackSpace` still ends the server (`quit-compositor`). Without a login process to ask (no session bus, or nobody owns `org.cupertino.Login1`: a headless or capture run) the `logout` shortcut ends the server as it did before the panel existed. This also holds while `cupertino-login` restarts after a crash (up to a second, the name has no owner): `Super+Shift+Q` then ends the server without the confirmation panel.

The router forwards the power key's press when it is consumed and its release when the key goes up, and swallows the repeats of a held key. The worker awaits these two calls in turn, so the login process sees them in order. The login process times the hold (0.35 s and 1.5 s, `PowerButtonSleepsSystem`) and shows the power-button panel. With the session locked the router forwards the key to the lock screen and sends nothing. The process takes a logind `handle-power-key` block inhibitor so that the key reaches the server instead of powering off. The server receives the key only from a device it has opened as an input device (not checked on hardware). With the greeter nobody owns the name, so each press and release logs the warning below and nothing else happens. A call that fails (no session bus, the process is not running) is logged as a warning naming the process. The application menu registrar and the StatusNotifier watcher belong to the menu bar process.

### Shell processes

Backdrops are capped (`app_effects_v1.rs`): 64 per surface and 128 per client, counted from `get_backdrop` to the backdrop's destruction (the client disconnecting included); past either limit the server posts `too_many_backdrops` on the effects object, which ends the connection, and nothing is added. The protocol lets a surface hold several backdrops (the notification centre puts one behind each visible card), so the per-surface limit is a bound well above legitimate use and the per-client limit is the one that counts. The limits are constants, not configuration. `tests/app_effects_v1.rs` covers both limits, the freed place and a second client.

The server offers `cupertino_app_effects_v1` to every client and `cupertino_shell_v1` to the shell processes (`render/cupertino-protocols`). A client can ask for **backdrops** below its own surfaces (`app_effects_v1.rs`): a material recipe name, a rounded rectangle and an alpha, double-buffered with the surface's commit and drawn by the material pass directly below that surface; from version 6, `set_glass` (style, container, spacing) draws it as glass instead (*Glass pass*; the `large_panel` style from version 10, which a backdrop of an older version cannot name), and an unknown style or a negative spacing is `invalid_glass`. A window's square backdrop is cut to the window's rounded corners, as its content is: the window's rounded clip becomes the region's mask in the material pass (a region reads what is drawn below it, so it cannot be drawn apart and clipped) while it still draws within its own rectangle; without the material pass the fill that stands in keeps square corners (`tests/window_popup_backdrop.rs`). The surface may be a window's toplevel or a popup of a window or layer surface (a context menu): a popup with a backdrop is drawn over its material with the 1 device pixel rim and the panel row of the shadow table, which menu windows use, cut out under the popup (`popup_backdrop_elements`; `tests/window_popup_backdrop.rs`).

From version 11 (`SUBSURFACE_BACKDROPS_VERSION`) the surface may be a subsurface, such as a toolbar a client puts over its window so the content scrolls under it: its backdrops are drawn directly below the subsurface and the subsurfaces placed below it, above the rest of the tree, and read what lies below. Each backdrop remembers whether its object's version allows this; one made through an older object draws nothing on a subsurface. The scene splits the tree there (`app_effects_v1::raised_parts`, over `split_tree`, unit-tested): each run of surfaces is drawn as one `Tree` piece limited to its surfaces' elements (`TreeSlice`), and the subsurface's backdrops go between the runs, through the same treatment as the root's for windows (rescale, crop, rounded clip) and window popups, and as layer surfaces' for layer surfaces and their popups. A tree whose subsurfaces have no backdrops stays one piece, as before. A subsurface's glass reads and draws only within the subsurface's rectangle (`GlassContainer::bounded`), so a commit of the root under it recaptures and damages no more than that rectangle. The tone of a small shape (*Tone of the face*) and Reduce Transparency, Increase Contrast, the appearance, full screen and every scale work as for the root's backdrops. `tests/subsurface_backdrops.rs` covers the content under the bar, an object below version 11, the display options, an inactive and a full-screen window, a window across two displays, the tone, the damage of a commit under the window and input passing through the bar.

**Shell roles** (`authorization.rs`). A client of the public socket holds no capability. The server makes a connection with capabilities only for a process it starts: the supervisor for each `"shell"` entry (the roles of its `"roles"` list) and for the two built-in processes (*Built-in processes*: the portal Capture alone, the polkit agent Prompt alone), and the screenshot launcher (Capture and Session). The capabilities (`ClientCapabilitySet` of `ShellRole`: Session, MenuBar, Dock, WindowManager, SessionLock, Capture, Prompt) are server-side data of that connection. Prompt is the authentication prompt's, held only by the polkit agent's connection: no global or request needs it, it makes `cupertino_shell_v1` visible no more than Capture does, and no configuration file can name it or Capture (no `ShellRoleName` maps to either). Its layer surfaces are left out of every capture and screenshot (*Screenshots*), and while one is mapped on the overlay layer no application holds the shortcuts or the pointer. It draws on layer surfaces only: an `xdg_toplevel` of a Prompt connection is a protocol error (`xdg_wm_base.role`) that ends the connection, so no window of it reaches the window list, a window capture or an output capture. Its overlay surfaces are stacked above every other overlay surface, mapped earlier or later, for drawing and for hit testing (`authorization::layers_stacked`), and while one is shown (`prompt_shown`) the keyboard goes to the prompt only: another surface's exclusive keyboard request is ignored, a click on another surface gives it no keyboard, a popup grab of another client is refused, and a popup grab open when the prompt takes the keyboard is ended. The session lock stays above it: the locked frame draws the lock surfaces alone, and they take the keyboard; the prompt keeps its exclusive claim under the lock and gets the keyboard back at the unlock. There is no token to copy: another process, another connection of the same process id, and another session cannot hold a role, and a connection holds no role it was not made with (a dock does not hold the window manager role). Checks, in three places:

* *Bind time.* `cupertino_shell_v1` is visible (`can_view`) only to a connection with a shell role, the capture globals only to Capture, and `ext_session_lock_manager_v1` only to SessionLock (the lock screen; `lock` checks the role again). For any other client the global does not exist: binding it by the name another client sees is a `wl_display.invalid_object` error.
* *Request time.* `get_menu_bar`, `get_dock`, `get_session` and `get_window_manager` each need their own role (error `cupertino_shell_v1.permission`, 2, and an inert object); every request on a dock, menu bar or window manager object checks the role again.
* *Object ids.* A request on an object id the client never created ends the connection (Wayland's own object table), so a guessed id cannot reach a role object of another client. The same table keeps `cupertino_app_effects_v1` to a client's own surfaces and backdrops; the handlers also compare the surface's client, so a surface of another client is `invalid_surface`.

* *Permits.* A role request is checked by type: the dispatcher takes a `Permit<role::Dock>` (and the like) with `authorization::permit`, and `create_dock`, `create_menu_bar`, `create_window_manager` and `create_session_observer` ask for that permit, not a boolean; a permit for another role does not fit.
* *Holder.* The supervisor (and the screenshot launcher) binds each connection to the process it started with a pidfd taken right after the spawn (`shell_connection::bind_holder`; the child is not waited for yet, so its pid cannot belong to another process). The capabilities end when that process exits: a connection kept open by anything else (a descriptor passed on, a leftover child) holds nothing, and its shell objects answer every request with the permission error. At most one holder has a role of an output (one dock, menu bar and window manager each); a restarted process that asks for its role before the server has seen the old connection close gets it, because the roles of connections whose holder exited are released first (`release_revoked_roles`). A connection with no bound holder holds nothing (in-process test clients get an explicit detached holder, whose capabilities end after an hour: `DETACHED_LIFETIME`); if binding fails the supervisor ends the child and retries after the throttle, and the screenshot launcher ends it and logs the failure. A slow cold start loses nothing: the roles apply as soon as the spawn returns, and no token times out. Every request refused for a missing role logs one warning with the client, the interface and the role, and a session observer whose holder exited is told nothing more.
* *Who names a privileged process.* The `"shell"` list and the `screenshot` key start processes with roles, so only a system file may name them. Which file that is comes from the layer, never from where a path resolves: `/etc/cupertino/compositor.json` and `/etc/cupertino/greeter.json` (the login screen's server), named exactly, are system layers, and every other file, `$CUPERTINO_SERVER_CONFIG` included, is the person's (a link to a system file is the person's file). A system file is opened once without following links, checked on that descriptor (a regular file owned by root that no one else can write), and read from it; a file that fails is refused. Only programs the install put in place count: an absolute path under `/usr` (or the install prefix the server was built with, `CUPERTINO_INSTALL_PREFIX`, which must be absolute and not `/` at compile time) without `..`. An entry that fails this is refused with a warning; an entry with no roles is not screened. An entry naming a built-in process, by its name (`portal`, `polkit-agent`) or by its program's file name, is refused in every layer, `--dev-shell` included (*Built-in processes*). The person's file (`~/.config/cupertino/compositor.json`, or any file outside `/etc/cupertino`) can remove or reorder the system's entries, and add processes without roles; it cannot add a process with roles, change an entry's command or roles, or set `screenshot`. `--dev-shell` lifts this for every file, for a checkout (`run-cupertino.sh`, `scripts/capture.sh`) or a nested run; nothing turns it on by itself. The shell list and the screenshot command are read at start, not on a settings change.

The `"shell"` key of the configuration lists the processes to start (`[{"name": "notifications", "command": ["cupertino-notifications"]}]`, empty by default; the optional `"roles"` list is `["session"]` unless it names `menu_bar`, `dock`, `window_manager`, `session_lock` and `clipboard` as well). The supervisor (`supervisor.rs`, `restart_policy.rs`) restarts a process that exits with failure, at most once per second, and leaves a process that exits successfully stopped. It wakes only when a child exits (its pidfd becomes readable) or a restart is due (a timer at the earliest one): no poll runs while every child runs; a child whose pidfd cannot be opened is looked at every 100 ms instead. Each child also gets a connection of its own as `WAYLAND_SOCKET` (`shell_connection.rs`), holding the roles of its `"roles"` entry (*Shell roles*). The children get the server's `WAYLAND_DISPLAY` (for the programs they start) and `XDG_CURRENT_DESKTOP=Cupertino` (also every client the server starts), so the session's desktop-specific files (`cupertino-mimeapps.list`, `OnlyShowIn=Cupertino`) apply to them. The `notification-center` and `launcher` actions go through the D-Bus worker (*Session bus*). A layer surface above the windows that commits exclusive keyboard interactivity takes the keyboard (the launcher panel while it is shown) and gives it back to the key window when it stops asking or goes away; while the session is locked only a shell process can take it.

**Built-in processes** (`config.rs` `BuiltIn`, `supervisor.rs`, `cli.rs` `publish_session_when_ready`). The server starts two processes no file names: the portal, `bin/cupertino-portal`, with the Capture role alone, and the polkit agent, `bin/cupertino-polkit-agent`, with the Prompt role alone. Each program is looked for at that fixed path under the install prefix, then under `/usr`; the supervisor runs it like a `"shell"` entry (its own connection, restarted with backoff), and a program that is not installed is logged once and not started. A program someone other than root could have put there or could change is refused with a warning and the next root is tried, so a stale copy under the prefix does not shadow the packaged one (`config::check_built_in`): the program and its `bin` directory must be no links, neither may be writable by its group or by others, `bin` must have the install root's owner, and the program must be root's, or the user's own under a prefix the user owns (a development install). The check runs again before every start, so a program changed after it ran is not restarted; it waits out the throttle and is checked again. They start in a user session only: with `--udev`, and not on the login screen (the server of `/etc/cupertino/greeter.json`, or `XDG_SESSION_CLASS=greeter`); nested and headless runs start neither. Before the session is published to the user manager (*Session bus*), the server waits for the portal to own `org.freedesktop.impl.portal.desktop.cupertino`, so that the portal frontend started by an application finds it, for at most `PORTAL_READY_TIMEOUT` (5 s). The wait runs on the D-Bus worker and a loop timer, so the server draws and takes input meanwhile; on the timeout it logs a warning and publishes without the portal. When the portal is not installed, or there is no session bus, the session is published at once.

**Menu-bar role** (`get_menu_bar`, `menu_bar.rs`; see *Rendering*): the server reserves the bar's height, applies hide / reveal / dimming, feeds it the active application and menu addresses, and runs its window commands. A surface that is not a layer surface of the output, already has a shell role, or an output that already has a bar is a `role` protocol error.

**Dock role** (`get_dock`, `dock.rs`): the dock process draws the bar, the switcher's panel, the overview chrome and the context menus, and lays out the overview. The server supplies the window feed, minimize target, the switcher's list and selection, the overview's window set and workspaces, and maps hot corners and gestures to named actions. the client owns the dock's presentation and its reserved area (the layer surface's exclusive zone, the standard layer-shell usable-area path). The server sends every window (`window`, `window_closed`, `done`-delimited; the first group on bind) and `launching` when it starts a program. From shell version 19 it also sends `app_resident` (after the window events of the group) for every application a public client has mapped a window of while that client stays connected, windows or not: an application whose last window closed but whose process runs keeps its dot. The connection's end (an exit or a crash) is noted through the client's `gone` hook and sends `app_resident` with 0 at the next tick; the first group of a new dock lists every resident application, so a dock that came back after a restart drops the ones that went meanwhile. The server's own connections, the shell processes and the X11 satellite (whose one connection carries every X11 application's windows and outlives each of them) are never resident. It takes `activate_app` (the window model's `ActivateApp`), `restore_window` (unminimize, animating out of the tile) and the double-buffered `set_minimize_target`. The same `role` error applies (one dock per output).

**Application switcher.** The dock draws the panel. The server keeps the keys and the choice (`input.rs::switcher_key` and `cupertino-wm`'s `focus.rs`). While the switch is open every key goes to it and none to a client:

* Tab / Right / Shift+Tab / `` ` `` / Left step. A fresh press wraps, a key repeat stops at the ends, and Shift pressed or released mid-repeat turns it round.
* Home / Page Up and End / Page Down jump to the ends.
* Return / Space commit. Escape /. cancel.
* Up / Down / `1` / `! commit and open the application overview.
* Q asks every window of the selected application to close. H hides or shows it.
* The release of the primary modifier commits. For the first 150 ms only the count of steps is kept (the hidden counter).

Only applications with a window are listed, and an application whose last window closes leaves the list. The group for a change goes to one dock, the one on the output under the pointer when the switch opened (else the first dock): `switcher_output` (that dock client's object for the output, its own output when it has none), `switcher_entry` per application, most recently used first, then `switcher_changed` with the selection. The end (`switcher_closed`) reaches every dock. A dock that binds mid-switch on the panel's output gets the state at once. `switcher_select` (the pointer over or on a tile) moves the selection, `switcher_activate` (the left button released on a tile) selects and commits, `switcher_cancel` (released on the panel off the tiles) cancels. A press anywhere but the panel (layer namespace `cupertino-dock-switcher`) is the server's and its release cancels the switch. Without a dock, or with a dead one, the switcher opens, steps and commits the focus unchanged and is invisible. `cupertino-dock` creates an overlay surface on the named output when the switch opens and destroys it when it ends.

**Screen reader at the login screen** (`screen_reader.rs`): the login screen's server (the one `config::login_screen` names) makes itself undumpable at its first line, before any other process of the greeter's user exists; when that fails it takes nothing and the login screen has no reader. Otherwise it takes descriptor 3 when `CUPERTINO_READER_FD=3` names a socket there (the session manager's worker gave it); it marks it close-on-exec and removes the variable, so no shell process or client has either, and every other server removes the variable and takes nothing. It sends `ready <socket>` once its Wayland socket is known, and `toggle <socket>` when Super+Alt+S is pressed on a keyboard: the chord is matched in `keyboard_event_now` on the keys from the input devices before the router, the overlays and any shortcut inhibitor, and its key and release go to no client. No client request, assistive technology action or bus call reaches the toggle. The worker's answers (`on`, `off`, `unavailable`) are logged; the on-screen notice is not drawn yet. The login screen's server starts no program (`Cupertino::login_screen`): no terminal, no screenshot process, no `exec:` binding and no `--spawn`, whatever a key, a client or a bus call asks; only its shell processes and Xwayland run under it. The session manager lets only the leader's descendants connect to `greeter.sock`, so a program started there would pass that check.

**Screen reader at the lock screen.** Super+Alt+S is the one shortcut that acts while the session is locked, on purpose: a person who needs the reader to unlock can turn it on at the lock screen. It is matched before the router, as at the login screen, and only starts or stops the reader; every other binding of either profile is forwarded to the lock screen (`KeyRouter::key`), VT switching aside.

**Screen reader in a person's session** (`screen_reader.rs`, `SessionReader`): a session on the hardware (udev mode, not the login screen) looks up its reader once at start, the first of `cupertino_defaults::accessibility::SCREEN_READERS` (`/usr/bin/orca`) that only root can change, the login screen's rule; nested and offscreen runs have none. The server runs it as its own child while `screen_reader = on` in `accessibility.conf`: every change of the accessibility settings, at start included, starts or stops it to match (`Cupertino::sync_screen_reader`). The reader gets its own process group, standard input from `/dev/null` and the server's environment with `WAYLAND_DISPLAY`, `XDG_SESSION_TYPE=wayland` and `XDG_CURRENT_DESKTOP`; it is held by a pidfd and reaped by a thread. Stopping sends `SIGTERM`, then `SIGKILL` after 2 s. Settings' Screen reader switch sets the key with `SetAccessibility("screen_reader", "on"|"off")`. Super+Alt+S on a keyboard turns the reader off when it runs and on when it does not, and stores the key the same way; like the login screen's chord it is matched before the router, the overlays and any shortcut inhibitor, so no application or `shortcuts.conf` line can take it while a reader is installed, and without one it is an ordinary key. A reader that ends by itself is not restarted until the chord, the switch or another accessibility change asks for it while the key is on.

**Keyboard shortcuts inhibit** (`shortcut_inhibit.rs`, `input.rs`): an application such as a virtual machine, a remote desktop client or a game can ask to receive the keys the system would act on. The compositor decides: an inhibitor is active only while its surface has the keyboard focus, its client is an application (not a shell process) that answers its pings (`hung.rs`; an unresponsive client holds nothing until it answers again), the session is not locked, no authentication prompt is shown (a mapped overlay layer surface of a connection with the Prompt role, `Cupertino::prompt_shown`) and the person has not released it. An inhibitor active when the prompt maps is ended at once (the commit or destruction of a prompt surface refreshes every hold) and is active again once the prompt is gone. While one is active `KeyRouter::key` forwards every key but the reserved actions (`Action::is_reserved`: VT switching, `lock`, `power-key`, `power-dialog`, `quit-compositor`, `release-shortcuts`), matched on the physical chord before anything else sees the key; the input-source HUD, the accent picker, the key rewrite for third-party clients and the Super tap are off. A notice (`SceneLayer::CompositorOverlay`, above fullscreen windows, left out of a locked frame) names the chord of `release-shortcuts` first and then the application, for 3 s; the application's name comes from the client, so it is shown without control or bidi characters and at most 48 characters long. The supported output width is 320 logical points and up, at any scale, measured with the real font: (a) the sentence that names the chord ("Press <chord> to get your shortcuts back.", "... your pointer back." for a pointer constraint, "... your input back." when the window holds both) is shown whole for chords up to the tested length (`Super+Escape`, `Ctrl+Alt+Escape`), in a slightly smaller type on a narrow output and with the application's name left out when it does not fit; (b) for a longer configured chord the chord itself is shown whole, alone, in the smaller type (11.5 points): every chord of the four modifiers and a key name of the table, a function key or a keypad digit fits in the 280 points left (320 less 8 points of margin and 12 points of padding on each side), measured with the real font in a test; the widest, `Ctrl+Alt+Shift+Super+XF86MonBrightnessDown`, is 262 points. The chord is what matters; the sentence around it is a courtesy. Below 320 points nothing is guaranteed: the notice shows the chord alone, cut at the output's edge. Only an application toplevel holds the shortcuts: a layer surface, a popup or a lock surface never does. That chord (default `Super+Escape`) ends the inhibitor of the focused surface and releases its client, so a window it maps afterwards holds nothing either: the client stays released until one of its windows gets the keyboard focus again from the person's own input (`Cupertino::as_input`: a key plan, a pointer button, a request of the dock, the menu bar or the window manager process), never from a client request (`xdg_activation`, the gtk shell, a window that maps), so an application cannot take the shortcuts back by moving the focus itself. A button press of the person's on the window that already has the focus arms it again too (`Cupertino::arm_by_press`). A release chord the active keymap cannot type gets the default bound beside it (checked at start and when the keymap or the layout changes).

**Pointer constraints** (`pointer_constraints.rs`, `events.rs`): `zwp_pointer_constraints_v1` lets an application lock the pointer in place or confine it to a region of its surface, with the relative pointer for the motion. The compositor decides: a constraint is active only while its surface, or one of its subsurfaces (games and video draw in one), is under the pointer and belongs to the window with the keyboard focus, that window may hold the shortcuts (the rules above: an application toplevel, a client that answers its pings, the session unlocked, no authentication prompt shown; a lock or confine active when the prompt maps ends then and is taken again after), the person has not released it, no move, resize, popup grab, overview or switcher runs, and the pointer is inside the constraint's region (with the surface's input region). While a lock is active `pointer_moved_to` leaves the position alone and sends only relative motion, so no hot edge, shake or drag sees it move; when the lock ends on the surface the pointer goes to the client's cursor position hint if that is on the surface. While a confine is active a motion is clamped into the region, sliding along its edge. The constraint's activation shows the notice above, once per focus of the window or release (Smithay itself ends a constraint when the pointer crosses into a subsurface, and it is taken again at once); the notice goes as soon as the window holds neither the shortcuts nor the pointer, however that ended (`Cupertino::settle_hold_notice`, also when the client destroys its constraint); the release chord gives back the pointer with the shortcuts (`release-shortcuts` is consumed while either is held, and a held pointer alone leaves every other shortcut to the system), and the same rules arm the window again. The cursor is the client's (hidden, if it asks) while a constraint is active; a window the person released cannot hide it (`Cupertino::cursor_choice` shows the default cursor for `Hidden`). Known limits: a client can still set an invisible cursor surface; when the pointer crosses between a confining surface and its subsurface the client gets `unconfined` and `confined` again in the same pass, as Smithay ends the constraint on that pointer focus change; touch and tablet constraints and `zwp_pointer_warp` are not offered.

**Foreign parents** (`handlers.rs`): `zxdg_exporter_v2` hands a client a random 32-character handle for one of its toplevels; the handle names no window and ends with the export object or its client. A client that imports the handle and calls `set_parent_of` makes the exported toplevel the parent of its own, and the parent reaches the model through `parent_changed`, as `xdg_toplevel.set_parent` does. A parent that is not a window is no parent, and an unknown handle is destroyed at once. Limitations: a withdrawn export clears the parent but sends imports no `destroyed`; only the last child set through one export is cleared; an exported surface that is not a toplevel is not refused, it simply never becomes a parent; both globals are offered to sandboxed clients.

**Activation** (`handlers.rs`, `cupertino-wm::activation`): every xdg-activation token is kept with its creation time and whether it may activate (made by the server for a program it starts, or by a client for an input event while it had the keyboard focus). A token is used up by its first request. A mapped window's request brings it forward when its token is valid, at most 2 s old, newer than its application's last activation, and no key or button press came more than 100 ms after the token. A request for a surface that has no window yet is kept (only when valid) until the window maps, or dropped when the surface is destroyed. Otherwise the request is refused, logged (`activation refused`) and, for an application not in front, sent to every dock as `attention` (the dock bounces the tile once). `gtk_surface1.present` and `request_focus` are activation requests too: a window of the client that has the keyboard focus is brought forward; any other request is judged by the token `request_focus` names as startup id (`present` names none, so it is refused), so a client with no input behind it cannot take the keyboard from another application.

**Application browser.** It is the launcher's: the `app-grid` shortcut (and the dock's own mapping of a corner or gesture, which the dock sends back as `run_action("app-grid")`) ends in `ShellOp::ToggleAppGrid`, which calls `org.cupertino.Launcher1.ToggleApplications` on the session bus. The server keeps no browser state, so without the launcher the action does nothing. The launcher opens the browser in its panel (or unfolds its search field into it), folds it back on Escape and closes it on a second action, a further Escape, a click outside the panel, a launch or the session lock. Docks are no longer sent `toggle_app_grid`.

**Window-manager role** (`get_window_manager`, `window_manager.rs`; one per output, else the `role` error): the process owns the stage policy and the server keeps the frame clock.

* The server sends the usable area and the arranged windows (mapped, unminimized, parentless toplevels of the output's current workspace whose application is not hidden: `window` with application id, frame and active state, `window_closed` when one leaves the set; `done`-delimited, the first group on bind), `toggle_stage` on the `toggle-stage` action (no default chord), and `strip_pressed` for a left press on a strip thumbnail with no window or top or overlay layer surface above it (the press reaches no client).
* The process answers with `set_placement` (stage, strip rectangle or hidden) per window, applied together on `commit`, and `activate_window` (`Command::FocusWindow`).
* On commit every window whose placement changed is retargeted from where it is drawn now, on three tracks with the stage model's springs, all critically damped (springs, for the strip): the frame with response 0.38 s, the alpha with 0.30 s and the corner radius with 0.20 s, from the window's own radius (12 pt) to the strip's 8 pt and back. Each track keeps its value and velocity when retargeted; the frame is one spring on x, y, width and height, headed for the window's own frame; when that frame changes during the swap (the client resized or the window was moved) the track turns towards the new one, keeping its value and velocity. The mask's shape is part of a masked element's commit, so a corner-radius change alone damages the window. A strip window is its live content and decorations scaled into its rectangle (the overview's path, not a capture), its content, title bar and rim masked to the animated radius and its shadow drawn with it, below every stage window, with no hit testing of its own. A window placed hidden keeps its frame and fades out (alpha 1 to 0), then is not drawn; it comes back in its new place fading in, with that place's corners. The alpha values per placement (1 on the stage and in the strip, 0 hidden) are approximate: gives the alpha spring, not the values the design's modifiers write.
* When the object goes away, also when the process dies, every window is back at its own frame at once. A window leaving the arranged set loses its placement the same way. With the stage off the process sends no placement.

**Hot corners and gestures** are detected in the server (every corner arms; dwell 0.0 s, `hot_corner_dwell` and `hot_corner_size` in `compositor.json`; the recognizer's swipe up / down, pinch and spread) and sent to the dock of the output as `hot_corner` and `gesture`. The dock maps them (`dock.conf`) and answers with `run_action` (a named action of the shortcut file, run as its chord would: `overview`, `app-overview`, `show-desktop`, `launcher`, `lock`, ...), its own grid or a program. Without a dock a corner or gesture does nothing, except that a committed gesture still leaves an open overview. `app_command` serves the dock's tile menus: `show_windows` opens the application overview, `hide` and `quit` run the application's commands. The `focus-dock` action (Ctrl+F3 under `cupertino`, Super+F3 under `classic-pc`) sends `engage` in a group of its own to the dock of the output under the pointer, else to the first dock, only to docks of shell version 18 or later and never while the session is locked; the dock answers by asking for exclusive keyboard interactivity on its bar.

**Scroll count** (`cupertino_scroll_v1`, `scroll_v1.rs`): `wl_pointer` cannot carry the scroll count, so a client binds the global, calls `get_scroll(wl_pointer)` and gets `scroll_count(axis, count)`. For every touchpad scroll event that sends an axis value, `Cupertino::pointer_axis` sends one `scroll_count` per moving axis to the scroll objects of the client that has the pointer focus, after the `wl_pointer.axis` events and before the `wl_pointer.frame`; events the coalescing holds back and the gesture-ending stop send nothing. The count comes from `cupertino_input::ScrollCounter` per touchpad (`PointerDevice::scroll_count`): the first event of a gesture is `Began`, the next ones `Changed`, the stop `Ended`. A count of 0 means no series has started. Wheels have no gesture phases, so the design gives them no count either: their frames carry no `scroll_count`, which a client reads as 0.

**Session observer** (`get_session`, `session_v1.rs`): every shell process creates one and follows the session from it, instead of a `--dark` flag. Right after creation it gets `appearance` (1 dark, 0 light) and `locked` or `unlocked`, then one event per change.

* The appearance changes at run time through `Cupertino::set_appearance` (the `toggle-appearance` action, bindable in `shortcuts.conf` or `compositor.json`, no default chord).
* `locked` is sent when the lock request is accepted, before the lock screen has its first frame, and `unlocked` when the session opens again. A lock whose client crashed stays locked and sends nothing, and a client taking it over does not send `locked` a second time.
* The request needs the Session role (a shell process). Any client of the socket may observe the appearance and display options alone through `cupertino_app_effects_v1.get_appearance`, which has no lock state.
* An appearance observer's `display_options` also carry `always_show_scroll_bars`: set for `show_scroll_bars` `always`, clear for `when-scrolling`, and for `automatic` set while a mouse is connected (a pointing device other than a touchpad that has moved, scrolled or clicked). It is sent again when the setting changes, a mouse is first used or a mouse goes away (`Cupertino::sync_scroll_bars`).
* From version 9 they also carry `steady_caret`, the `steady_caret` key of `accessibility.conf`: an observer of version 9 or later is told when only it changes, an older one is never sent the bit.
* A version 2 observer (`cupertino_shell_v1` version 2) also gets `display_options` (a bitfield of reduce motion, reduce transparency, increase contrast and differentiate without colour) after `appearance` at creation and once per change. A version 1 observer never does.
* **Opening an application** (shell version 20, `activate_app(serial, desktop_id)`, `Cupertino::activate_desktop_app` in `dock.rs`): the launcher asks for the application of a desktop file ID when the person chooses it. An application matches when its identity is the ID (with or without `.desktop`), or the server's desktop entry for its identity (by ID, `StartupWMClass` or program) has that ID, without regard to case; of several, the most recently active. One with a window the dock would list (not created, closing or destroyed) gets the dock's `Command::ActivateApp`, so the same rules hold: the frontmost window takes the focus, a minimised window is restored when it has no other, a hidden application is shown. The answer is `app_activation(serial, activated)`; without a window it is `resident` (a client that showed a window of it is still connected, as for the dock's `app_resident`) or `not_running`. The server starts nothing: the launcher launches, or asks the resident process for a window. The Session role is checked on every request (`require`): a connection whose process exited gets `permission` and nothing is done. A public client never sees the shell global, so it cannot reach the request; the shell processes with the Session role are installed programs the system configuration lists (a user configuration cannot add one with roles), and the dock role already raises applications the same way.

### X11 applications

X11 programs run through [`xwayland-satellite`](https://github.com/Supreeeme/xwayland-satellite) (0.8 or later; it runs `Xwayland`, so both must be installed), started on demand (`xwayland.rs`). At start, outside headless runs, the server takes the first free X display from `:0`: its lock file `/tmp/.X<n>-lock` (a lock whose process is gone is taken over) and its two sockets, the abstract `@/tmp/.X11-unix/X<n>` (bound first, so a display another server holds is skipped) and the file `/tmp/.X11-unix/X<n>`. The socket directory must be a real directory (not a symbolic link) of root or of the user, sticky if others can write to it. It is not created when missing (systemd-tmpfiles makes it at boot, owned by root): the owner of a sticky directory may replace any socket in it, so one made by a user could take over other users' X displays; without it the session runs Wayland-only and the log says why. Nothing runs until the first X11 program connects. Then the satellite starts with both sockets (`:<n> -listenfd <abstract> -listenfd <file> -auth <file>`), the server stops watching them, and the satellite shows each X11 window to the server as an ordinary `xdg_toplevel` of a public-socket client with no shell role, so X11 windows follow the same window policy, focus and input as every other window. Every program the server starts, the shell processes and (on a shared user bus) the user manager get `DISPLAY=:<n>` and `XAUTHORITY`. Programs the server starts and the shell processes also get `XDG_SESSION_TYPE=wayland` and, unless the program or the session already set them, `QT_QPA_PLATFORM=wayland;xcb` (Qt 5.11 and later try Wayland, then X11) and `ELECTRON_OZONE_PLATFORM_HINT=auto` (Electron before 38; later versions pick Wayland from `XDG_SESSION_TYPE`), so toolkits that would take X11 because `DISPLAY` is set prefer Wayland and fall back to X11. On a shared user bus the two hints are also published with `DISPLAY` to the user manager and the activation environment, so programs started by D-Bus activation or as user units choose the same way, but only where the manager has no value of its own (the user's `environment.d` wins); the names published are recorded in `$XDG_RUNTIME_DIR/cupertino-session-defaults`, and `cupertino-session` removes exactly those when the session ends. `SDL_VIDEODRIVER` is not set: an SDL 2 bundled with a game may not accept a list, and a name it does not know fails its video start. The authority file (`$XDG_RUNTIME_DIR/cupertino-xauth-<n>`, mode 0600) holds a fresh random `MIT-MAGIC-COOKIE-1`: the abstract socket has no file permissions, so without the cookie any local user could reach the display. When the satellite exits, the server watches the sockets again: after a successful exit at once (which also starts the throttle over), after a failure (a crash too), a successful exit within a second of its start (it could not run) or a child that cannot be waited for, only once the restart throttle of the shell processes has passed (1 s, doubling to 30 s), so the next X11 program, or one that was already waiting, starts it again and a satellite that cannot run is not started in a loop. X11 programs that were running lose their windows with it. The supervision of the shell processes watches its exit (a pidfd) and kills it when the server ends; the lock, socket and authority files are removed then. Without `xwayland-satellite` on `PATH`, or when no display can be taken, the log says so, no `DISPLAY` is set and the session serves Wayland clients only. Clipboard and primary selection between X11 and Wayland programs are the satellite's (it bridges them as a Wayland client); drag and drop between them, and the scale of X11 programs on outputs of different scales, are the satellite's limits (it uses one scale for all X11 windows). The scale is the satellite's too: as the display's XSETTINGS manager it publishes `Xft/DPI` (96 × scale × 1024), `Gdk/WindowScalingFactor` and `Gdk/UnscaledDPI`, and writes `Xft.dpi` into `RESOURCE_MANAGER`, from the smallest output scale. `ci/vm/x11_apps.py` checks it in a QEMU guest at scale 2 with `xterm` (the three settings, the resource and a window twice its size at scale 1) and copies text from a Wayland window to X11 and back (`cupertino-testclient --copy`, `--clipboard`; an X11 program receives the Wayland selection only while it has the keyboard focus).

### Glass pass

`render/glass.rs` (`GlassElement`, part of the material pipeline's GL objects) draws glass backdrops: those a client gave `set_glass` (version 6 of `cupertino_backdrop_v1`) and those with a glass material name (`Glass`, `ClearGlass`, `LargePanelGlass`; `app_effects_v1::GLASS_MATERIALS`), which the toolkit's menus, popovers and `PaintCx::glass` use. The scene joins the glass backdrops of one surface that share a nonzero container into one `Container` of `cupertino-glass` (`GlassGroups` in `render/scene.rs`), drawn where its frontmost backdrop is; a popup's glass (a menu, a popover) gets the menu outline along its sides and the menu's light rim inside, keeps the panel shadow and, in the plain dark recipe, lays a dark grey face fill (`POPUP_GLASS_FACE_DARK`, `0.235` at `0.49`) over its face so the panel reads dense over any backdrop; Reduce Transparency, Increase Contrast and the light appearance keep the recipe's face. The recipe is `cupertino_theme::GlassParams` of the appearance, the style and the display options (`accessibility::glass_mode`), sized by each shape.

**Tone of the face.** A container whose shapes' union has a shorter side under `SMALL_CONTROL_SIDE` (64 pt) adapts its foreground: its shapes are probes (`ToneProbe`, part of the container's identity). When its textures are made again (the backdrop changed), the widest used blur level is drawn into a grid of at most 32 × 32 texels and read into a pixel buffer behind a fence (`ToneRead`, at most 8 at once); `process_screenshots`, after each output's frame on every backend, polls the fences without waiting, takes each probe's mean texel (`grid_mean` over `probe_uv`), its face (`face_luminance`: `cupertino_glass::glass::face_color` of the mode and the shape's size) and its tone (`cupertino_theme::glass::face_tone`, with the last tone sent as the hysteresis), and `BackdropTones` sends `tone` to backdrops of version 7 only when it changes; a backdrop of a container that does not adapt, or one drawn as a material other than glass, is sent `appearance` once if it had a tone. Nothing is drawn, read or sent while nothing under the glass changes; frames are asked for only while a read is pending, once the output's clients were called back (`poll_tones_again`: asked for before, the callbacks would settle the request and a read the GPU had not finished would wait for some other change). The tone tells a client one bit per small backdrop about what lies behind its window. Tests: `tests/backdrop_tone.rs` (the events over a black and a white wall, a control that stops being glass, light glass, a version 6 client, and the contrast of labels drawn in the tone's colours over walls of saturated colours, in both appearances and with Increase Contrast, against the bare face beside them in a capture), `app_effects_v1::tests`, `render::glass::tests`.

1. The element covers the container's sampled area: the union of its shapes grown by the reach of its widest blur and its refraction (`Container::sample_area`).
2. When the backdrop changed, that area of the bound framebuffer (found through the frame's projection, so flipped and rotated outputs work) is blitted into a texture at half scale, and each blur level a shape reads (and the blur fill) is blurred from it with the downsample and Gaussian passes of the material pass, into textures kept for the container.
3. The composite (`glass.vert/frag`, copies of `cupertino-glass/shaders/gles/`) shades the smooth union of the shapes from those textures, once per damage rectangle, with the blend state (SRC_ALPHA, ONE_MINUS_SRC_ALPHA) / (ZERO, ONE).

**Invalidation.** `finalize_materials` gives a glass element the signature of the elements below it whose geometry overlaps its sampled area (`area_generation`): a change elsewhere on the output, or above the glass, keeps its textures and draws only the composite; a change under it (content, geometry or the opacity it is drawn at) advances the element's commit, so the damage tracker repaints the whole area and the capture reads a freshly drawn backdrop. Elsewhere the framebuffer still holds the last frame with the glass on it, so textures are made only with the commit advanced: `GlassCache` keeps the textures of every container the frame being built shows (past its limit of 16 if need be), one capture per output a container shows on, and gives back the least recently drawn of the others past the limit, and those that have not drawn for 2048 draws. A container whose textures it gave back is reported once when it shows again, and its element advances its commit, so it is captured from a freshly drawn area. An unchanged element keeps its commit, so a frame that draws something else repaints only that. Unit tests: `render::material::glass::tests` (the capture rectangle and its texture mapping, the signature, the cache policy and the element's commit) and `render::scene::tests::glass_reblurs_only_when_what_lies_below_its_sampled_area_changes`, `glass_backdrops_of_a_surface_join_per_container_where_the_frontmost_is`.

**Check against the CPU model.** `tests/app_effects_v1.rs::glass_pass_matches_the_cpu_model` draws a 400×160 glass panel over the procedural wallpaper and compares every pixel around it with `cupertino_glass::glass::Container::shade` (the wallpaper changes slowly enough that each blur level of it is the wallpaper itself): light, dark, dark with Reduce Transparency and light with Increase Contrast stay within a mean of 0.3 and a maximum of 2 (8-bit). `glass_pass_over_sharp_content_reads_the_backdrop_where_the_model_does` puts icon-sized squares and thin bars under a dark panel, one square under its left edge, and compares the pass with the model fed Gaussians of the shot without the glass: it matches within 2/255, and a model reading its backdrop 2 pixels off misses by over 20, so the capture region, its texture mapping and the refraction offset are where the model has them.

### Accessibility display settings

`accessibility.conf` (`cupertino-defaults::accessibility`, `$CUPERTINO_ACCESSIBILITY_CONF` overrides the path) is read at start in the winit and udev modes and written on every change; offscreen runs keep the settings in memory. The server is its only reader and writer (`accessibility.rs`): it applies the settings to its own drawing and tells the shell processes the four display options. Actions `toggle-reduce-motion`, `toggle-reduce-transparency`, `toggle-increase-contrast` and `toggle-differentiate-without-color` (no default chords; bindable in `compositor.json`'s `keybindings`, not in `shortcuts.conf`, whose parser knows only the shared shortcut table's actions) flip one option; `Cupertino::set_accessibility` replaces them all. The machine's defaults, `/etc/cupertino/accessibility.conf` (`SYSTEM_ACCESSIBILITY`, written by an administrator), are read with the system-file rules (no link, owned by root, writable by no one else; otherwise ignored and logged) and only their allowed keys (`SYSTEM_KEYS`: `reduce_motion`). They are the settings of the login screen, whose account has none, and of every key an account's own `accessibility.conf` does not record, and a change of that file applies to them at once (it is watched). The person's file records only the keys they changed (`PersonalAccessibility`); a key stays theirs once changed, even when set back to the machine's value. A file with every key, as earlier versions wrote it, stays valid and keeps every key the person's. Offscreen runs read no machine file.

| Setting | Server drawing |
|---|---|
| Reduce Transparency | materials take their `-Opaque` variants (`RenderResources::recipe`, cached per appearance and option); glass keeps its shape and takes its reduced-transparency recipe (`accessibility::glass_mode`): no refraction, a much wider blur and a dense fill |
| Increase Contrast | the high-contrast catalogs (`Cupertino::appearance`), so materials are opaque too; decorations take the high-contrast palette and the contrast half of the shadow table; glass takes its increased-contrast colours, and with both options the reduced-transparency optics with them |
| Reduce Motion | glass takes its reduced-motion recipe (no refraction band, a wider narrowest blur); `render::motion`: the workspace switch cross-fades in place instead of sliding; full screen draws the new frame at once (no frame zoom, the workspace cross-fade carries the change); an opening sheet fades in at its resting place without the slide (`skips_sheet_slide`) and a closing sheet disappears at once; the warp and funnel minimize effects become the scale effect, with its timing, and the scale then also fades out towards the dock slot and back in on restore (`minimize_opacity`) |
| Colour filter, invert, display contrast | a `Full` material element over the whole output in `SceneLayer::DisplayFilter` (below the pointer): backdrop at scale 1 without blur, then the colour chain of `cupertino_glass::display_filter` |
| Differentiate without colour | broadcast only |

The design filters the pointer too; here it stays above the filter pass so pointer motion does not repaint the whole output. The colour filter and invert are read from the file only: no action changes them at run time. Without the material pipeline (no GLES 3) the filter pass is not drawn; the pipeline failure is logged once at start.

```ini
rewrite_terminals = foot, kitty, Alacritty, org.wezfurlong.wezterm, com.mitchellh.ghostty, org.gnome.Terminal, org.kde.konsole, xterm   # app ids, exact and case-insensitive (approximate)
rewrite_off = firefox       # app ids that never get a rewrite
fn_key = change-input-source  # tap action of the fn key: do-nothing, emoji, dictation
caps_lock_switch = off      # on: a caps-lock tap switches the input source, a hold turns caps lock on
caps_lock_hold = 500        # ms a caps-lock press must last to count as a hold, 1-1500 (default)
layout_keyboard = ansi      # key arrangement of `decoded:` sources: ansi, iso, jis
layout_level3 = right-alt   # level-3 keys of `decoded:` sources: both-alt, right-alt, none
compose_key = right-alt     # compose key of the system layouts: off, right-alt, right-ctrl, menu, caps-lock, scroll-lock; unset keeps localed's; its grp: switch keys are left out
slow_keys = off             # a key counts only once held for the delay
slow_keys_delay = 250       # ms                                                      (default)
sticky_keys = off           # modifiers latch for the next key, a second tap locks
sticky_keys_shortcut = off  # five Shift presses within 30 s toggle sticky keys
mouse_keys = off            # the keypad moves the pointer
mouse_keys_shortcut = off   # five Alt presses within 30 s toggle mouse keys
mouse_keys_delay = 1000     # ms before a held direction key repeats                  (default)
mouse_keys_max_speed = 11   # points per 50 ms tick                                   (default)
```

System layouts stay the groups of one keymap and come back when a system source is chosen. approximate defaults (the values is not known): both shortcut toggles off, `caps_lock_switch` off, level 3 of decoded sources on the right Alt only (both Alt keys would take Alt away from the shortcuts).

* **Repeat**: `wl_keyboard.repeat_info` advertises `RepeatConfig::repeat_info`: 500 ms / 83 ms becomes 12 characters per second with a 500 ms delay (tested with a real client); with slow keys on both become 420 ms. Clients do the repeating. The compositor repeats, with the same values, only keys it consumes itself: one `KeyRepeater` (`kbd_filters.rs`, polled from the overlay tick) replays a held key through the HUD / accent / shortcut router while the key and the same modifiers stay down. Stepping actions repeat (switcher open and cycle, window cycling, relative workspace switch, overview navigation, input-source step, volume and brightness steps; approximate), as do the HUD's Up / Down and the popup's Tab / arrows. Toggles (mute, overview open, launcher ...) never repeat.
* **Filter chain** (the design keyboard filter's order): device keys pass slow keys, the caps-lock delay (skipped while slow keys are on), sticky keys, mouse keys, then the router.
  * Slow keys: a press is delivered once held for the delay, an early release drops both events, a second key while one is pending is rejected.
  * Sticky keys: a lone modifier tap latches it for the next key (its release is held back and sent after that key), a second tap locks it, a third unlocks. With the shortcut on, five Shift releases within 30 s toggle the feature.
  * Mouse keys: keypad 8 / 2 / 4 / 6 and the diagonals move the pointer one point, then after the delay every 50 ms with the verified ramp up to the maximum speed. Keypad 5 clicks, 0 holds the button,. releases it (keys ). With the shortcut on, five Alt presses within 30 s toggle it.
  * A key the TTY backend reports as already held when it reads a device (open after a session switch, `SYN_DROPPED`) skips the filters until its release, so the Ctrl and Alt of a `Ctrl+Alt+F<n> switch do not arrive latched in the new session.
* **Fn key**: a tap (held no longer than the repeat delay, no other key in between) runs `fn_key`. `change-input-source` steps to the next source; `emoji` and `dictation` are logged as unavailable.
* **Modifier profile**: the compositor's own shortcuts are matched on the physical keys (Shift, Ctrl, Alt, Super), whatever the profile; each profile has its own table. `cupertino`: Super carries the system chords (`Super+Tab` switches, `Super+w` closes), Ctrl keeps its own. `classic-pc` follows Windows and Linux habits: `Alt+Tab` switches (releasing Alt commits), `Alt+F4` closes, `Super+arrows` tile, `Super+Down` restores a tiled or zoomed window before it minimizes, `Super+Tab` is the overview, the Super key pressed and released alone opens the launcher (a tap: no other key and no pointer button between, held under 750 ms, not while the session is locked or with sticky keys latching Super; a line `Super = launcher` in the shortcuts file binds it, `Super = none` frees it), and the chords of the applications (Ctrl+W, Ctrl+Q, Ctrl+Tab, Ctrl+Space, Ctrl+Shift+arrows, F11) are never taken. No chord of Ctrl+Alt and a character is bound under `classic-pc`: AltGr is often typed that way. The profile's `Profile::translate` (`cupertino-modifiers`) still gives the logical modifiers that applications and the text fields see. Switching the profile at run time rebuilds the bindings; the menu bar is told the new chords.
* **Input sources**: the list becomes the XKB layouts of the seat keyboard (`XkbConfig` layout / variant lists), so clients get one keymap with several groups. `Ctrl+Space` (previously used source) and `Ctrl+Alt+Space` (next source in menu order) are the design assignments. The first press opens the HUD in most-recently-used order and moves the selection, further presses step, releasing the modifiers commits (`Return` commits, `Escape` cancels), and a chord without held modifiers switches at once. `Up` / `Down` step the open HUD. HUD visuals: radius 24 pt, minimum width 167 pt, padding 10 pt, rows of 40 pt, white tint at alpha 0.35, 0.3 s fade-out. The material (`Menu`), the placement (centre of the primary output) and the source icons (two-letter placeholders) are approximate / unknown. Row labels are the XKB layout names.
* **Caps lock**: the press is held back and delivered only if the key is still down after the delay (a calloop timer; a brushed key vanishes completely),. With `caps_lock_switch = on` and two or more sources the delay is `caps_lock_hold`: a shorter press switches to the next input source (the design toggles between the last two ABC / non-ABC sources; next source is the adaptation), a longer one turns caps lock on.
* **Accent picker**: hold a letter key. On its first repeat the popup opens next to the text cursor. `Tab` / arrows move the focus (shown as marked text), `1`-`9` pick directly, `Return` commits, `Escape` restores the base character, any other key closes it and is delivered. A click on a candidate commits it, a click elsewhere in the popup is taken, a click outside closes it (approximate). A held letter with candidates reaches the client as a press and an immediate release (the input method gets the repeats), and the compositor's own repeater opens the popup, so no extra base character is inserted; the physical release is swallowed.
  * Text reaches the application through `zwp_text_input_v3`. Smithay serves text input only while an input method is connected, so with an accent table the compositor connects an in-process `zwp_input_method_v2` client (a thread behind a socket pair). It learns which application has an active text input, receives its cursor rectangle through an input popup surface, and sends `delete_surrounding_text`, `set_preedit_string`, `commit_string` and `commit`. Applications without text-input support (plain terminals) never activate the bridge, so the picker does not start for them. Verified end to end with a real client (a terminal committed the chosen character).
  * The candidate lists are user data (nothing embedded; `tests/fixtures/accents.json` is a small authored sample).

### Launcher

The panel is drawn by the `cupertino-launcher` process (see its README); the server renders its backdrop and toggles it. `Super+Space` (`launcher` action, hot corner) calls `org.cupertino.Launcher1.Toggle` through the D-Bus worker. The process holds one overlay layer surface, created without an output each time the panel opens so that the server puts it on the output under the pointer. While the panel is shown it takes the keyboard (see *Shell processes*). The supervisor starts and restarts it through the `shell` key, for example `{"name": "launcher", "command": ["cupertino-launcher", "--terminal", "foot"]}`; without that entry `Super+Space` only logs a failed call. The `--no-launcher-files` flag and the `launcher` / `launcher_files` keys of `compositor.json` no longer exist (the parser ignores unknown keys): pass `--no-files` to the process, or leave it out of `shell`.

### Volume and brightness overlay

The volume, mute, display-brightness and keyboard-backlight keys go to the `cupertino-osd` process (see its README), which changes the level and shows the overlay. The default bindings (`XF86AudioRaiseVolume` / `LowerVolume`, `XF86AudioMute`, `XF86AudioMicMute`, `XF86MonBrightnessUp` / `Down`, `XF86KbdBrightnessUp` / `Down`, plus Shift+Alt for the fine step) call `org.cupertino.Osd1.VolumeStep` / `ToggleMute` / `ToggleMicrophoneMute` / `BrightnessStep` / `KeyboardBrightnessStep` through the D-Bus worker; they are bound only where the shortcut table leaves the chord free, and rebindable as `volume-up`, `volume-up-fine`, `volume-mute`, `microphone-mute`, `brightness-down-fine`, `keyboard-brightness-up` and so on. Start the process with the `shell` entry `{"name": "osd", "command": ["cupertino-osd"]}`; without it a key press only logs a failed call. The compositor repeats held stepping keys (see *Keyboard*), so holding a key steps repeatedly.

### Screenshots

The five screenshot shortcuts are the actions below. Each starts the program of the `screenshot` configuration key (default `["cupertino-screenshot"], see its README) with the mode appended. One process runs per capture; the server does not supervise it.

| Action | Default chord | Arguments appended |
|---|---|---|
| `screenshot` | `Super+Shift+3` (and `Super+Shift+S`) | `--mode screen` |
| `screenshot-clipboard` | `Super+Ctrl+Shift+3` | `--mode screen --clipboard` |
| `screenshot-area` | `Super+Shift+4` | `--mode selection` |
| `screenshot-area-clipboard` | `Super+Ctrl+Shift+4` | `--mode selection --clipboard` |
| `screenshot-toolbar` | `Super+Shift+5` | `--mode toolbar` |

The process gets a connection of its own and runs on it with the Capture and Session roles:

- `Cupertino::privileged_client` inserts one end of a socket pair as a client holding them (`ClientState::capabilities`);
- the other end is passed as `WAYLAND_SOCKET`, and `WAYLAND_DISPLAY` is removed.

Only a connection with the Capture role sees the capture globals. Copy sessions go on while the session is locked, from the lock request on (before `locked` is sent): a frame of an output source is all opaque black, so neither the lock screen nor what it covers is copied, and a frame of a toplevel source waits, unanswered, until the unlock. A session made while locked gets its constraints like any other. While locked the window feed is not refreshed. The layer surfaces of a connection with the Prompt role (the authentication prompt) and their popups are left out of every image that leaves the compositor: capture frames, `--screenshot` files and recordings (`SceneParams::for_capture`, set only by `Cupertino::draw_output_image`); the screen shows them. A copy session whose connection no longer holds the Capture role (its process exited) is stopped at the next rendered frame or the next frame request, and shows no longer as running. While a layer surface of namespace `cupertino-screenshot` (the overlay or the toolbar) is mapped, a further shortcut starts nothing. The log has `screenshot process started` and `screenshot process exited` with the pid and the exit status.

Capture (`src/capture/`):

- **Sources.** An output source renders the output once more offscreen at its mode size, through the normal element tree. The pointer is drawn only when the session asks for it (`paint_cursors`). A toplevel source renders the window at its natural size like the window snapshots: frame and decorations, no shadow.
- **Buffers.** shm only, ARGB8888 and XRGB8888. The session announces the buffer size of the source's current placement.
- **When frames are copied.** After the source's output was rendered.
- **Damage.** A frame reports the rectangle that changed since the session's previous frame; the first frame is all damage.
- **Unchanged source.** A frame of an unchanged source waits for a change.
- **Sources that go away.** A session whose output or window is gone is stopped; its waiting frames fail with `stopped`.
- **Cursor sessions.** These are stopped at once: the cursor is not offered as a separate image.

`cupertino_screenshot_v1` sends the windows on screen front to back for the window pick:

- the foreign-toplevel identifier;
- the frame with its decorations, in global points, where the workspace slide puts it.

It sends them on bind and again whenever the list changes.

### Display power and idle

`display_power.rs` decides, `power.rs` carries it out. The settings are `power.conf` (`cupertino-defaults::power`, read at start and on every change (*Live settings*); `$CUPERTINO_POWER_CONF` overrides the path; an invalid line is logged and skipped): display and system sleep per power source, `dim_before_display_sleep`, `require_password_after`, `lock_screen_display_sleep`. The defaults are the design's (display sleep 10 min on mains power and 2 min on battery; password after 300 s), except system sleep: never on mains
power, because nothing says a build, a download or a remote session is running (none takes a sleep inhibitor), and 10 min on
battery.

| Step | When (T = display sleep of the current power source) |
|---|---|
| dim | T - 15 s after the last input, to brightness factor 0.01 in 0.26667 s |
| lengthened countdown | input within 20 s of the dim undims (0.26667 s) and sets T to max(min(2T, 600 s), T) until the display sleeps |
| display sleep | T after the last input; instant. DRM: the CRTC is disabled (DPMS off) and no frame is queued; elsewhere the dim overlay goes fully black |
| lock | the display has slept for `require_password_after` (`never` disables it): `Lock` on `org.cupertino.Login1` |
| system sleep | the system sleep timer after the last input: logind `Suspend(false) |
| wake | any input event (keys, pointer, touch, gestures): the display is on at once, a full redraw, the ext-idle notifier gets the activity too |
| fade-in on activation | logind makes this session the active one again (a console switch back, a fast user switch): a black overlay over every output fades out over 0.25 s with `e = 0.5 (1 - cos(pi p))`, alpha `1 - e`; logged as `fading in from black` |

An idle inhibitor (`zwp-idle-inhibit-v1` on a live surface, or a logind `idle` inhibitor in `BlockInhibited`) holds the countdown at its start without lengthening it. The power source follows UPower's `OnBattery` (`cupertino-powerd`); without UPower the mains timers apply and that is logged. Resume from sleep (`PrepareForSleep(false)`) counts as input. The dim is a black overlay above everything on every output, with alpha `1 - encode(f)` where `f` is the brightness factor and `encode` the sRGB transfer, so that the dimmed light is `f` of the full (the design scales the backlight); the ramp is a raised cosine (approximate, the curve). Log lines: `display power state=dimmed|asleep|on`, `the display slept for the password delay: locking the session`, `idle: putting the system to
sleep`, `power source on_battery=…`, `logind idle inhibitor blocked=…`, `the system woke from sleep`.

### Live settings

`live.rs` watches `compositor.json`, `keyboard.conf` and `power.conf` (`cupertino_defaults::watch`, from start in every
mode) and applies a change while the server runs. Only the changed file is read again, with the last values read as the
last good ones: a wrong line or key keeps its value and is logged (`invalid configuration: the key keeps its value`). Only
the keys whose value changed in the file apply, so a setting changed another way (the `toggle-appearance` action) stays
until its own key changes; a key removed from the file goes back to its default. Log line: `configuration reloaded`
(`keyboard settings reloaded`, `power settings reloaded`).

| File | Applied at once | At the next start |
|---|---|---|
| `compositor.json` | appearance, tracking speeds, acceleration (the pointer devices start over with the new curve), scroll direction, cursor size, colours (the cursors are recoloured) and shake, minimize effect and closing animation (with the window model's minimize timing), hot corner size and dwell, corner radius, scroll bars (the appearance observers are told), key bindings, terminals, screenshot command | `decorations` (windows that open from now on follow it), `menu_bar_height`, `show_menu_bar`, `shell` |
| `keyboard.conf` | every key; input sources and the layout keys rebuild the keymap, repeat changes are sent to the clients | — |
| `power.conf` | every key; the countdown in progress continues with the new timers | — |

### Quitting the applications before a log out

`quit.rs` serves `org.cupertino.Session1` at `/org/cupertino/Session1` on the session bus (from its own thread, started with the D-Bus worker); the login process's session agent calls it between the confirmed log out and logind (`shell/cupertino-login`):

| Member | What it does |
|---|---|
| `QuitNextApplication -> (s app_id, u windows) | activates the most recently used application that has toplevels and sends `close` to each (`xdg_toplevel.close`); `("", 0) when none has a window |
| `ForceQuitApplication(s app_id) -> u` | SIGKILL to the processes of the application's toplevels by the rules of Force Quit (pidfd; never the server, a shell process or a proxy); returns how many. Only the session agent may call it (see Who may call below), any other caller gets `UntrustedCaller` (`AnonymousCaller`, `FlatpakCaller` or `SnapCaller` by class) |
| `ApplicationQuit(s app_id) | signal: the last toplevel of the application being quit went away |
| `SetAppearance(s appearance) | `light` or `dark`: stored as `appearance` in `compositor.json` (only that key changes), then applied as the `toggle-appearance` action applies it; `auto` is `NotSupported` (no time-of-day or location source), any other value `InvalidArgs`, a failed store, or no settings directory, `Failed` and nothing changes |
| `SetAccessibility(s key, s value) | one key of `accessibility.conf` with a value as the file writes it (`reduce_motion` `on`, `color_filter` `tint 0.5`, `screen_reader` `on`, which starts the session's reader): applied and stored like the accessibility shortcuts; an unknown key or bad value is `InvalidArgs` |
| `Appearance` (property `s`), `Accessibility` (property `a{ss}) | the session's appearance and every key of `accessibility.conf` with its value; `PropertiesChanged` on every change, by any path |
| `Mice` (property `a(ssub)`, read-only) | the connected mice, not the touchpads, each as `(key, name, dpi, stored)`: the `mouse_dpi` key of `compositor.json` (`vendor:product:name`, ids in hex), the device name, the resolution in use (stored, else the hardware database's `MOUSE_DPI`, else 1000) and whether it is the stored one; one entry per key; a mouse without a bus id (the winit backend's pointer) has no key, so it is not listed and cannot get a resolution; `PropertiesChanged` when a mouse is plugged or removed and when `mouse_dpi` changes |

The server stays the only writer of `accessibility.conf` and of the appearance: the settings application uses these members.

**Who may call.** Every caller of a method is identified from the `ProcessFD` of `GetConnectionCredentials` (`caller.rs`; the pidfd keeps the process id from being reused while it is judged) and classified like the desktop portal does: a process with `/proc/<pid>/root/.flatpak-info` is a Flatpak application, one whose `LinuxSecurityLabel` starts with `snap.` a Snap, and a caller that cannot be identified or classified is anonymous. A process that is not dumpable (the login process, which hardens itself) cannot be classified because `/proc` refuses the check; the server accepts it only when it is one of the agents it supervises and its pidfd is still alive, and refuses it as `UntrustedCaller` otherwise. `QuitNextApplication` and `ForceQuitApplication` are for the session agent (the supervised process with the `session-lock` role, that is the login process, and the server itself); `SetAppearance` and `SetAccessibility` are also open to the settings client (the program `bin/cupertino-settings` under `/usr` or the install prefix, as the unsandboxed process the person started; under `--dev-shell` any program of that name). A sandboxed caller is refused every one of these methods, even when it runs the settings program. Each refusal has its own error name under `org.cupertino.Session1.Error`: `AnonymousCaller`, `FlatpakCaller`, `SnapCaller`, `UntrustedCaller`, and logs one warning with the method, the process id and the reason (never the arguments). `ForceQuitApplication` holds the caller's pidfd, not a process id from the bus daemon's second answer. The properties stay readable by every caller.

Session-bus methods of other services are checked by the services themselves (`cupertino-peer`): `org.cupertino.Login1` and the step methods of `org.cupertino.Osd1` (see their READMEs); `org.cupertino.Login1` answers only the server, so the menu bar's session menu goes through `cupertino_menu_bar_v1.session_action` (role MenuBar), which the server forwards to the matching Login1 method (`Sleep`, `RequestRestart`, `RequestShutDown`, `LockNow`, `RequestLogOut`, `SwitchToLoginWindow`, `RefreshCapabilities`). The server names the supervised login process to the menu bars (`session_agent`, version 5), which read the agent's properties only from the owner of the name that is that process. The log out shortcut and the menu's Log Out reach the login process over its private connection (`cupertino_session_v1.log_out_requested`) while one is connected; only without one do they use the bus, where an owner of the name that is not the login process gets nothing and the session goes on. A log out that finds nobody on the bus ends the server like the shortcut does, but only when no login process is supervised: while one runs and has not taken its name yet (starting, restarting) the request is dropped with a warning and a banner from the notification service ("Log out did not start", also shown when the refused owner of the name is a squatter). `Launcher1.Toggle` and `Launcher1.ToggleApplications` answer only the server (the launcher's parent); `ControlPanel1.Toggle` answers any unsandboxed process, as the menu bar that calls it is no relation of the panel. `Settings1.ShowPane` stays open to every caller because it only changes what is shown. `Osd1.Show` is open for the same reason.

Residual case: an unsandboxed process can connect to the bus, pass the connection's descriptor on and then `exec` `/usr/bin/cupertino-settings`; the daemon names the process at the time of the call, so it counts as the settings application. It gains nothing it could not already do by writing the person's own files.

**The lock does not use the bus.** `lock_session` and `lock_session_now` (the lock shortcut, the idle lock, the menu's Lock) send `cupertino_session_v1.lock_requested` to the session observer of the connection that holds the session lock role, which is the login process the server started. Only when no such connection exists do they fall back to `Lock` and `LockNow` on the bus, where the verified-owner rule below applies. A process that took `org.cupertino.Login1` before the login process did therefore neither receives a lock request nor makes it go missing; the login process runs without the name (it logs an error) and the lock-before-sleep and logind lock signals work as before. The refused-owner log is an error. Power requests (`Sleep`, the restart and shut down panels, `RequestPowerDialog`, `PowerKey`, log out) have no such fallback: with the name held by another process they are refused and logged, and nothing is lost but the action, which the person sees did not happen and can repeat; the lock is the one request whose loss leaves the session exposed. A fallback for each would be a request on the protocol per action and a timing path for the power key. Known limitation: the menu bar reads the capabilities of whoever owns the name.

**Calls to the login process.** Before the D-Bus worker calls `org.cupertino.Login1` (`Lock`, `LockNow`, `RequestLogOut`, `RequestPowerDialog`, `PowerKey`) it asks the bus for the owner of the name, identifies the owner the same way, and sends the call to the owner's unique name only when that process is the supervised login process (`--dev-shell`: any owner). A squatter is refused with a warning, and a refused `RequestLogOut` is dropped, with the banner above, and the session goes on. The supervision timer keeps the trusted process id current across restarts of the login process. Known limits: a squatter that owns the name before the login process starts blocks the lock and power requests until it goes (the login process gives up on `NameTaken` and logs it); the checks identify the peer by pidfd only, so a caller in another pid namespace (nested containers without `/proc` of the host) is anonymous and refused. An unsandboxed program of the same user that is not the settings client is refused too, but a program that replaces the settings binary under `/usr` is out of scope (that needs root).

The 45 s timeout, the 0.1 s pause and the interrupt panel are the agent's. The order is approximate (most recently used first). Log lines: `log out: asking the application to quit`, `log out: the application quit`, `log out: force quit`.

## Integration points

Everything above is built in. The `ShellExtension` trait is gone; the shell processes take its place.

* **Decorations**: with `decorations = false`, `Config::window.ssd_insets` reserves the space and nothing is drawn in it.
* **Pointer buttons**: a press the server consumes (overview, decoration, `Super` move or resize) also consumes that button's release (`consumed_buttons`), so a client never gets a release without its press; a client's own press and release go through the seat's implicit grab, and a model move the client asked for still ends with the client getting its release.
* **Element types**: `CupertinoElement` has variants for surfaces, shader rectangles, materials, CPU-drawn images (`Image`), rescaled decorations (`Decoration`), and mesh textures (`Mesh`); `render::mesh::capture` renders any element list into a texture, `MeshElement` draws it through a `cupertino_effects::Mesh`; `ElementCache` gives stable ids.
* **Input**: `Cupertino::process_input_event` accepts any Smithay `InputBackend` event (winit, evdev); `events.rs` documents the order: menus → decorations → shell → model interaction → client. Scripted input: `Cupertino::pointer_moved_to`, `pointer_button`, `gesture`. Relative motion of every pointer device goes through a per-device `PointerDevice`: the device's counts through the design curve family (`cupertino_input::PointerAccel`; touchpads use their own family and report rate). Wheel detents scroll 10 points per line, unaccelerated: a wheel, high-resolution or not, has no scroll resolution. Touchpad finger scrolling goes through `cupertino_input::ScrollAxisAccel` per axis (trackpad scroll curves, resolution 400, 67 Hz, setting 0.3125) and its lines become 10 points each. Momentum stays with the clients (they run kinetic scrolling after the finger source's axis stop; a server momentum would double it). Natural scrolling follows `natural_scrolling` for touchpads (on by default) and `mouse_natural_scrolling` for wheels (off by default), per device class (`PointerSettings::natural_scrolling_for`). * **Stage**: the policy is the `cupertino-windowmanager` process's (on `cupertino-stage`); the server only applies its placements (`window_manager.rs`, see *Shell processes*).

## Daily-driver known limits

What is open for using Cupertino every day, as of this file. Nothing here has a date. "Not run on hardware" means it has only been tried headless, nested or in a virtual machine; a real session on a discrete GPU with one 4K monitor has not been run yet.

* **First real session.** Starting Cupertino from a display manager (GDM) on real hardware, with the NVIDIA driver, has not been run (*From the display manager*).
* **NVIDIA.** Explicit sync (the release point is signalled once the flip of the last frame drawn from the buffer is done) has not run on NVIDIA. Lock, unlock, sleep and resume, and log out, restart and shut down through logind, are not run on hardware either.
* **GPU reset.** On a display the server makes a new renderer and the windows stay (*GPU reset* below); recovery from a real reset has not been run on hardware.
* **Portals.** `cupertino-portal` serves the appearance settings, the file chooser, the app chooser that asks which app opens a link or a file, screen sharing and screenshots (`data/cupertino.portal`). Screen sharing shares one display or one window for each request as a PipeWire stream, in shared memory only, with no cursor metadata, no region source and no audio; a display the person lets the app keep is shared again without asking from its restore token. It has not been run with a browser on a real session. A screenshot asks the person first and saves every display as one PNG, and a colour pick answers with the pixel the person clicks.
* **Authentication prompt.** `cupertino-polkit-agent` is in the packaged binaries and the session starts it. Hardware acceptance of administrator prompts remains open.
* **Audio.** The volume and mute keys change the default PipeWire sink and the microphone mute key toggles the default source (*Volume and brightness overlay*). With no PipeWire daemon, volume and mute fall back to the ALSA master mixer.
* **X11 applications.** Started through `xwayland-satellite`; the server tests use a fake satellite, and the real one is checked in a QEMU guest only (`ci/vm/x11_apps.py`: scale 2, clipboard both ways). Outputs of different scales give every X11 window the smallest one.
* **Terminal.** The ISO and installer ship `foot`. Other installations need a supported terminal on `PATH`.
* **Crash recovery.** A server crash ends the session and returns to the display manager; windows are not reopened.
* **Long runs.** `ci/soak.py` is the soak run (server memory, open descriptors and frame pacing every minute); no result from the hardware is recorded here.
* **Input methods.** An input method framework (fcitx5, ibus) cannot attach; the input-method global is given only to the compositor's own accent bridge.
* **Drag and drop and the primary selection.** Drag and drop is tested between two Wayland test clients only. The primary selection is not kept after its source application closes.
* **Screen recording, night light, DDC/CI brightness.** Not implemented. Screenshots work.
* **Several monitors and a second GPU.** Tested in a virtual machine only.

## Open issues and approximations

* **Shell roles.** The capabilities are per connection, not per process id: the socket pair's other end is the credential, so a shell process that passes its descriptor on passes its roles. The server starts every shell process, and the descriptor is inherited by the process it starts only (`WAYLAND_SOCKET`, close-on-exec cleared in the child alone). A process the supervisor starts through another program (`env`, a shell wrapper) holds the roles of its entry. A `"shell"` entry without `"roles"` holds Session alone, so a configuration written before the roles existed loses its dock, menu bar and window manager until the entries list them (the packaged `compositor.json` does).
* **Public effects.** Any client may create backdrops and choose its title bar style on its own surfaces, and observe the appearance. A client can therefore ask for as many backdrops as it likes; the server does not limit them.
* **Request-time re-checks.** The check on each request of a dock, menu bar or window manager object (`authorization::require`) fails once the holder exited and the connection is still open; the permission error on `get_*` also fails for a connection that never held the role.
* **Descriptor passed to another live process.** The holder binding ends the roles when the process they were made for exits, not when another running process uses the descriptor: the server cannot see which process writes to a socket pair (`SO_PEERCRED` of a pair the server made names the server). Only the process the server started gets the descriptor, and it is not meant to hand it on.
* **Authentication prompt.** Only the built-in polkit agent holds the Prompt role. The prompt is recognised by its connection alone: any overlay layer surface of that connection with a buffer counts as shown, whatever its size or place. `--screenshot` files and recordings leave the prompt out but still show the lock screen (only copy sessions are black under the lock). Another surface's exclusive keyboard request made while the prompt is shown is ignored until that surface commits again after the prompt goes away, and a popup grab refused while it is shown leaves the popup open without the grab.
* **Portal restart.** The portal readiness wait is for the start of the session alone. After the portal exits, its bus name is unowned until the supervisor restarts it and it takes the name again (a second or more, with backoff): a portal request in that window fails, and the application has to ask again. A wait that timed out leaves its watch on the D-Bus worker until the name is first owned.
* **Exclusive keyboard at the lock.** An application's layer surface that asks for exclusive keyboard interactivity while the session is locked is ignored until it commits again after the unlock.
* **Programs under `/usr`.** The install-path rule trusts the files of `/usr` as installed by the package; it does not follow symbolic links out of `/usr` or check the owner of the program.

* **X11 applications.** Started on demand through `xwayland-satellite` (*X11 applications*); untested here with real applications on hardware; in a QEMU guest scale 2 and the clipboard both ways are checked (`ci/vm/x11_apps.py`), while drag and drop, popups, full screen, cursors, primary selection and mixed scales are unverified. An X11 program started before the server published `DISPLAY` (or by a service of another session) does not reach the display. The display and its cookie stay the same for the whole session; a satellite crash costs the X11 programs that were running.

* **Resume after a VT switch.** A frame still waiting for its vblank when the session paused is dropped at the resume by clearing its output (one short black flash), since a driver that lost that vblank would otherwise hold every later frame of the output back. The clear is a blocking commit: when the driver did lose the flip it can stall the server once, up to the driver's own flip timeout (3 s in nvidia-drm 615). The path needs real hardware and has no automated test.

* **GPU reset.** On a display (the udev backend) every EGL context is created with `EGL_EXT_create_context_robustness` and the reset strategy `LOSE_CONTEXT_ON_RESET` where the driver has it (the vendored smithay's `EGLContext::new_with_reset_notification`). Where the driver offers `EGL_NV_robustness_video_memory_purge` (NVIDIA), the context also asks for `EGL_GENERATE_RESET_ON_VIDEO_MEMORY_PURGE_NV`, so video memory the driver purged across a suspend or a VT switch is reported as a reset (`GL_PURGED_CONTEXT_RESET_NV`, `reason=the driver purged video memory`) and the renderer is remade, instead of drawing from lost buffers. Before each round of frames the server asks the render GPU's renderer whether the GPU was reset (`glGetGraphicsResetStatus`), and a frame that fails with the context lost counts as a reset too. On a reset (`src/gpu_reset.rs`) each card gets a new context and renderer on its EGL display, each display's buffers and second-GPU copies are made again, and so are the shaders, passes and outputs' damage; the window snapshots of closing ghosts are dropped. Client buffers are imported again by the next frame (their textures are kept per renderer), so the clients stay connected and nothing restarts. Each reset is one line in `session.log` (`<time> the GPU was reset: gpu=<card> reason=<who caused it>; <outcome>`), which `cupertino-diagnose` reports as `crash.gpu_reset`. A purge is routine (a suspend, a VT switch or a mode set may cause one) and is never counted; a fourth other reset within a minute, or a renderer that cannot be made, ends the session as a lost context does (*Lost rendering context*). `headless::simulate_gpu_reset` does the same offscreen for `tests/gpu-reset.rs`. Limitations: only the render GPU's status is polled (a reset of a second GPU is noticed by its next frame failing with the context lost); a client's dmabuf that the reset lost shows what the driver left in it until the client draws again; a driver without the extension reports no reset, so only a frame that fails with the context lost starts recovery; a driver that kept reporting purges would have the renderer remade each round, with no limit; recovery has not run against a real reset or purge on hardware.

* **Lost rendering context.** Without the udev backend's recovery (offscreen, nested), or when recovery fails, a lost rendering context ends the server with an error (exit status 1), so the session command and the display manager treat it as a failure and show the login screen. The error names the renderer's error and how many sessions on the hardware in a row ended this way (`$XDG_STATE_HOME/cupertino/lost-context-streak`, cleared by a session that ends otherwise), so a loss that recurs at every login shows in the journal.

* **Session desktop name.** `XDG_CURRENT_DESKTOP=Cupertino` reaches only the processes the server starts (clients and shell processes); applications started by D-Bus activation or as systemd user units get the environment of the bus or the user manager, so the session's `cupertino-mimeapps.list` and `OnlyShowIn=Cupertino` do not apply to them.

* **TTY backend.** Run only in QEMU (virgl, one connected output), never on real hardware or with two DRM displays (the start-up checks and logs of *Run on hardware* are written for the first run on a machine; SIGTERM is not handled: it ends the process at once, without the orderly shutdown of the quit key, and the kernel releases the devices); logind refuses control of a session that has a controller, so it cannot run inside the desktop session. Single GPU, hot-plug by rescanning, no mirroring, adaptive sync or custom modes. Output management and output power are proved headless only. Depends on `cupertino-seat`, `cupertino-devices`, `cupertino-evdev`.
* **Menu bar.** The reserved height is the configured `menu_bar_height`, and the bar surface is expected to have that height. The active output follows the pointer. Keyboard focus after a menu closes is the bar process's job (the server hands the keyboard to the bar on `engage` only). A click on a revealed bar overlaying a window also reaches the window's decoration under it. The title bar revealed over a full-screen window is drawn only on the live output, not in captures of the window or in the overview, and not while the window is transformed (`plan.exact`); a double click or a drag on it does nothing.
* **Dock** (`shell/cupertino-dock`). One minimize slot in the protocol, so the next-slot target is used for every window (no `minimize_to_app`). The dock's rectangle (where a minimized window flies in from in the overview) is its committed backdrop. The overview goes to the dock of its output only.
* **Windows.**
  * The kind is fixed at map. A later `set_modal` or parent change updates blocking and placement links, not the transforms. Documents and alerts have no protocol signal, so `Document` and `Alert` are never chosen.
  * A sheet hangs from the model's `titlebar_height` (approximate 28 pt), which fits the server-side title bar but not a client-side header bar (a GTK 4 Wayland dialog overlaps its parent's header bar). Sheets keep the server-side title bar the design's sheets lack.
  * A sheet's parent is dimmed with the `SheetUnderlay` material at the sheet's shown fraction, blended as an ordinary material layer, not the design's behind-window blend (approximate). Its content takes no clicks (the press brings the sheet forward, the title bar still moves the parent).
  * Non-sheet children centre on their parent (approximate). `closing_animation` opts plain windows into a fade. Utility panels float above normal windows and modal panels above both.
  * Every newly mapped window takes the focus, because a client without an activation token (most terminals) would otherwise never get it.
  * The switcher does not step on the scroll wheel, does not mirror the arrows for right-to-left layouts and has no alert sound or file-manager exception for Q. The label's compositing over the panel is approximate (see the dock's README).
* **Stage** (`shell/cupertino-windowmanager`). The alpha values a placement fades to are approximate (1 shown, 0 hidden; recovers the springs only), and the shadow keeps the window's active or inactive parameters instead of moving them with the 0.2 s corner spring as the design does. Thumbnails are flat (no 3D tilt, no app-icon overlay). Dialogs and other child windows of a strip window stay where they are. The strip does not hide when a stage window overlaps it (no edge-dwell path).
* **Effects.** Minimize captures the window each frame (a full offscreen render, fine for a handful of windows). The closing ghost is drawn above all windows. Snapshots are throttled (0.5 s), so a window that closes soon after its last repaint fades out with a slightly older image. The overview does not use the effect meshes (placed frames rescale).
* **Material backdrop.** The capture reads the framebuffer, so material elements drawn earlier in the same frame appear in a later one's backdrop (blur of blur where they overlap). The damage generation keeps this stable.
* **Pointer.** A mouse's delta is taken as raw counts. Touchpad motion and finger scrolling arrive in trackpad counts from `cupertino_input::Touchpad` (400 per inch). Mice use the default acceleration table on the speed of the hand in inches per second: counts over the device's resolution over real time, from the event timestamps summed over 8 ms, so the same hand movement gives the same cursor travel at any dpi and report rate; the curve gets that speed times 2.5, so a 1000 dpi mouse moves as the design moves raw counts (about 850 points per inch of hand at 2 inches a second, default speed). The resolution is the user's stored `mouse_dpi` entry for the device (key `vendor:product:name`, e.g. `046d:c077:USB Optical Mouse`), else the default entry of the hardware database's `MOUSE_DPI`, else 1000; a mouse's own dpi button is invisible to the host, so the stored value is how the user tells the server. The first report after a pause of a quarter second takes one period of the nominal 67 Hz. With `mouse_acceleration` off the gain is linear, per count of a 1000 dpi mouse. The touchpad's scroll is accelerated and then coalesced as the design's event translator does (events are held back until one exceeds 8 counts or 24 counts have summed up, and the sum goes out in whole points, what that truncates kept for the next one); `wl_pointer.axis` carries only the coalesced value. Every axis value is sent rounded to the protocol's 1/256 step with the rounding carried into the next value of the same axis, source and direction (`events::AxisCarry`), so single steps of a high-resolution wheel add up to a whole notch. The seat is offered at version 9: each frame carries the source (wheel, finger, continuous, wheel tilt), the 120ths of a wheel, the physical direction per axis (inverted under natural scrolling), the value, the time, and for a finger the stop that ends it. Wheels are neither accelerated nor coalesced (no scroll resolution on the design either); a notch (120 v120 units) scrolls 48 points, three lines of 16, in logical points whatever the output scale, and the v120 value goes along for toolkits that scroll by it. The touchpad's scroll count (the acceleration of repeated flicks) goes to clients through `cupertino_scroll_v1` (see Scroll count above). approximate: whether the design counts before or after the coalescing is not known, so the count is fed the points that are sent, and the events the coalescing holds back are skipped; the count is computed per device, one for both axes. The winit backend sees only absolute host positions, so acceleration is exercised on the TTY backend and in unit tests only. An absolute device (the winit window, a tablet in pointer mode) spans the output its pointer is on: its range covers that output's mode turned as shown, in panel pixels, which map to points through the exact scale (`Cupertino::output_pixels_to_global`), so the pointer lands where that pixel is drawn even when the logical extent is rounded.
* **Keyboard.**
  * Third-party clients get Super and Alt chords rewritten by the table §10 (`cupertino_keyboard::rewrite::decide`, applied in `keyboard_event_now`, `forward_rewritten` in `kbd_filters.rs`): Super+letter, digit, punctuation or Return becomes the Ctrl chord (Ctrl+Shift+C / V in terminals), and with an active `zwp_text_input_v3` Super+arrows become Home / End (with Ctrl for Up and Down) and Alt+Left / Right / Backspace / Delete the Ctrl word chords. Ctrl chords, claimed keys, function keys, Tab, Space and `cupertino-` clients are never rewritten. The client gets a `modifiers` event with the rewritten masks, then the key, then the real modifiers after the release. Open: Cmd+Backspace and Option+Up / Down have no toolkit-neutral spelling; the rewrite needs a runtime pass against GTK, Qt, Firefox and Chromium. `Resolver` stays with the first-party clients.
  * Decoded sources: Compose sequences for private dead-key states need the generated table installed as the clients' compose file. The control and command key tables are dropped, the keypad is the generic pc block, and each decoded keymap has a single group (switching swaps the whole keymap).
  * Sticky, slow and mouse keys have no indicator or sounds. The mouse-keys alternate letter keys are not implemented. HUD mouse selection is not wired. The fn key's `emoji` / `dictation` actions have nothing to open.
  * The accent picker needs a client with `zwp_text_input_v3`, and the popup falls back to the window centre without a cursor rectangle. Candidate lists are user data. The bridge occupies the seat's single input-method slot whenever an accent table is configured.
* **Session lock.** `locked` waits for a presented locked frame per output (page flip on the TTY backend, swap elsewhere), but a frame already queued when the request arrives is not cancelled, so one old frame may reach the screen before the black one. Smithay never clears its list of locked outputs after a lock client died; harmless, because the list is keyed by per-client output objects. Lock surfaces are drawn from the request on, before `locked`, which the protocol allows. Presentation feedback and frame callbacks of hidden clients wait for the unlock. Touch and tablet events are not routed, locked or not.
* **Launcher and notifications** (`shell/cupertino-launcher`, `shell/cupertino-notifications`). The server only renders their backdrops. The launcher panel opens on the output under the pointer.
* **approximate or unknown values.** The overview's spring form (its duration is as designed), gesture distances and finger counts, hot corner size, edge reveal delays of the menu bar, bar and popup colours and radius, popup shadow class, status icon size, snapshot interval, hidden-window frame callback throttle (1 s), wallpaper colours and the tint layer colour (wallpaper average), continuous corner expansion.
