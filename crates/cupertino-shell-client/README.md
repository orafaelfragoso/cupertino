# cupertino-shell-client

The privileged protocols of the shell processes as extensions on the transport's queue (`cupertino-wayland-client`).
GPL-3.0-or-later. Depends on `cupertino-wayland-client`, `cupertino-protocol-app`, `cupertino-protocols` (feature
`client`), `cupertino-geometry`, `wayland-protocols` and `wayland-protocols-wlr`.

## Public API

| Item | Contents |
|---|---|
| `LayerShell`, `LayerSurfaceConfig`, `Margin`, `LayerSurface`, `Layer`, `Anchor`, `KeyboardInteractivity` | `zwlr_layer_shell_v1` version 4 (on-demand keyboard interactivity): `bind`, `layer_surface(config)` returns a `LayerSurface` with the transport's surface (`surface`). `LayerSurface::configured(sent)` is the size to draw at: an extent the server left at 0 is the requested one, and 0 on both sides fails (`Error::Unsized`). `set_placement`, `set_exclusive_zone` and `set_keyboard_interactivity` apply with the next commit; popups of it work through the transport |
| `SessionLockManager`, `SessionLock` | `ext_session_lock_v1`: `lock` numbers each lock (`generation`), `lock_surface(output)`, `unlock` once confirmed, else `destroy` |
| `IdleNotifier`, `IdleWatch` | `ext_idle_notify_v1`: `watch(seat, millis)`; dropping it stops the events |
| `Shell`, `Session`, `AppActivation` | `cupertino_shell_v1` (versions 9 to 21): `session` observes the session, `observe` does so and reads its state before it returns (with the other events that arrived meanwhile, for the caller's loop), `menu_bar` and `dock` give a layer surface the role of an output. From version 20 `Session::activate_app(serial, desktop_id)` asks the server to bring a running application forward as the dock's `activate_app` does; the answer arrives as `ShellEvent::AppActivation` with the serial and an `AppActivation` (activated, resident, not running). Below version 20 it sends nothing and returns false |
| `SessionState`, `SessionChange` | dark, display options and locked as of the observer's last event; `apply(&ExtensionEvent)` takes one of them and says which changed, `None` for any other event. An application's `cupertino_protocol_app::Appearance` counts as well |
| `MenuBar`, `MenuBarUpdate`, `ActiveApp`, `AppWindow`, `Shortcuts`, `BoundAction`, `PrimaryModifier`, `WindowCommand`, `EditAction`, `WindowMenu`, `WindowState`, `GtkMenu`, `SessionAction`, `SessionAgent` | the menu-bar role, with `done`-grouped updates. From version 10 a group with `window_state` lists the application's windows and a group of its own carries the shortcuts; `activate_window` and the commands added in version 10 are not sent to a version 9 server. From version 11 `edit(EditAction)` has the server type an Edit item's chord into the key window (sent while the menu's popup still holds the grab); `can_edit` says whether the server takes it, and it is not sent below version 11. From version 12 `MenuBarUpdate::engage_help` is set by the Help search shortcut (open the Help menu with its search field focused), and the shortcut group may name `BoundAction::HelpSearch`. From version 13 `force_quit_app(app_id)` force-quits the active application without the dialog, only if `app_id` still names it when the server handles it; `can_force_quit_app` says whether the server takes it, and it is not sent below version 13. From version 14 `MenuBarUpdate::backdrop_lightness` carries, in a group of its own, the lightness of the wallpaper under the bar (CIE L*/100 in thousandths, capped at 1000) once the server has measured it; it is `None` in every other group and always below version 14. From version 21 `MenuBarUpdate::backdrop_bands` carries it in its place, in a group of its own: the mean encoded sRGB colour of that wallpaper band by band across the output (three channels from 0 to 65535 a band, at most `MAX_BACKDROP_BANDS`, 256, bands). From version 15 `window_controls` sets `WindowState::can_minimize` and narrows `can_zoom` to what both allow, in the group of its `window_state` (in either order); without it `can_minimize` is `true` and `can_zoom` is the server's `window_state` value. From version 16 `window_full_screen` sets `WindowState::full_screen`, in the group of its `window_state` (in either order); without it `full_screen` is `false` |
| `Dock`, `DockUpdate`, `DockChange`, `DockWindow`, `OverviewMode`, `OverviewWindow`, `OverviewWorkspace`, `Corner`, `Gesture`, `AppCommand` | the dock role, with `done`-grouped updates (from version 18 `DockChange::Engage`, the Focus Dock shortcut; from version 19 `DockChange::AppResident`, an application that runs with or without windows; from version 22 `DockChange::WindowThumbnail`, the picture of a minimized window, at most `MAX_WINDOW_THUMBNAIL` (256) pixels a side, `None` once it is no longer minimized; from version 23 `Dock::overview_drag`, `Dock::overview_move_window` and `Dock::overview_workspace_frame`, which do nothing on an older server); the switcher's output arrives as the transport's `OutputId` |
| `ShellEvent` | what the objects receive, inside the transport's `Event::Extension` and in order with its events: configures of layer and lock surfaces (acknowledged by the transport), `Closed`, `Lock`, `Idle`, `SessionLock`, `LockRequested`, `LogOutRequested`, `AppActivation`, `MenuBar`, `Dock`. The session's appearance and display options arrive as `cupertino_protocol_app::AppEvent` |
| `Error` | `Transport`, `UnknownOutput`, `InvalidShape`, `Unsized` |
| `test_clock` | `display_unix_seconds`, `display_now`: the clock a shell process draws with (the login screens' time, the dock's trash check, the launcher's caret). In a debug build `CUPERTINO_TEST_CLOCK=<decimal Unix seconds>` fixes the wall clock and freezes the monotonic one at the first reading, so the goldens settle; a release build (no `debug_assertions`) has neither the override nor the variable's name, which the release install test checks. Never for authentication, back-off, locks or IPC deadlines |

## Tests

```
cargo test -p cupertino-shell-client
```

Unit tests cover the menu-bar and dock groups, the configured size of a layer surface and the session state.
`tests/protocol-flow.rs` runs every role and `Shell::observe` against an in-process server.
